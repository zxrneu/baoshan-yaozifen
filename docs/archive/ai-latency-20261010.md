# AI 出牌延迟诊断与优化策略

> 历史记录：本文中的“当前”、配置、缺陷和测试数字只代表原日期；不作为今天的执行清单或默认值。替代入口见[归档索引](README.md)，返回[文档索引](../README.md)。

日期：2026-10-10。范围：当前默认浏览器 AI 的出牌阶段。本文制定后续实施方案；本次只新增基准和文档，没有修改牌桌行为或搜索算法。

## 1. 结论与已确认原因

出牌慢同时涉及**显示节奏、搜索预算、Worker 生命周期**。应先降低用户实际等待，再优化模拟热点，随后评估缩小预算对棋力的影响。

| 发现 | 代码依据 | 影响 |
| --- | --- | --- |
| 默认每次行动至少等待 650 ms；快速 260 ms，慢速 1200 ms | `src/hooks/useGame.ts` 的 `SPEED_MAP` | 正常模式三个 AI 连续行动至少需要 1.95 秒，即使立即算完也一样。 |
| 速度切换只改变显示等待 | `useGame.ts` 始终使用同一个 `browserOptimizedAgent` | “快速”仍使用默认搜索预算。 |
| 默认搜索热身 16 个牌局，上限 1024，时间 250 ms | `src/ai/optimized/contracts.ts` | 大量普通决策有机会持续计算到时间上限。已有 8/32、120 ms 的快速预设，但牌桌没有接入。 |
| 每张牌创建 Worker，成功返回后也终止 | `src/ai/optimized/workerClient.ts` | 重复模块加载、初始化和 JIT 预热；唯一合法牌也需启动 Worker。具体设备上的开销需浏览器实测。 |
| Worker 总请求超时为 1500 ms | `workerClient.ts` | 250 ms 只约束 Worker 内部搜索；启动、传输、调度可能让实际等待更长。 |
| 后续策略每步重建未知牌池并重复筛选 | `src/ai/optimized/policy.ts` | 相同历史、花色和敌人约束被大量重复处理。 |

当前延迟关系为：

```text
用户等待 ≈ max(显示最小等待,
               观察投影 + Worker 启动/传输/调度 + 搜索 + 返回处理)
           + 定时器调度及 React 绘制
```

搜索时间已经从显示等待中扣除，不能把它们直接相加。只优化计算而保留 650 ms 的显示等待，通常无法明显改善正常模式的出牌速度。

## 2. 计算复杂度是否过高

普通搜索的主要工作量近似为：

```text
信念 DP 建立 + W × (采样成本 + A × L × P + 配对统计成本)
```

其中 A 为活跃候选数（最多 12），W 为样本数（默认最多 1024），L 为每条模拟实际走牌步数（最多 48），P 为每一步的观察策略成本。配对计数每个样本约 O(A²)，候选淘汰等检查点处理另计。

- 默认理论规模可达 `12 × 1024 × 48 ≈ 59 万` 个模拟出牌步骤，但 250 ms 截止时间、获胜提前结束和候选淘汰会截断实际工作量。
- 信念分配采用记忆化 DP，容量状态上限为 `13³ × 5 = 10,985`，每个状态最多四个分支。没有枚举全部天文数量的暗牌组合。
- 小残局确有分支搜索，但限制为剩余手牌不超过 12 张、牌局不超过 256 个、节点不超过 5000，且单次尝试最多占 50 ms 或总预算的四分之一。

因此，主要问题是重复模拟和单步策略成本，普通出牌并非无限深的指数搜索。优先优化实现常数和预算分配，比立即重写算法更有依据。

统计提前结束也较保守：12 个候选、7 个检查点、误差参数 0.05 时，当前配对 Hoeffding 半径约为 `sqrt(19.65/n)`；16 个样本时大于 1，64 个样本时约 0.55。要确认 0.20 的胜率差约需 492 个配对样本，0.10 的差异约需 1965 个。因此不能指望小样本阶段频繁触发 `separated`。

## 3. 可复现基准

入口：[experiments/latency.test.ts](../../experiments/latency.test.ts)，原始结果：[experiments/results/ai_latency.json](../../experiments/results/ai_latency.json)。

```bash
AI_LATENCY_GROUPS=8 pnpm vitest run -c experiments/vitest.config.ts experiments/latency.test.ts
```

使用种子 61001 起的 8 副、全部 384 次出牌观察，固定叫 70 分，使用 `smartTrump/smartBury`，按信息受限策略 `observationPolicy` 生成同一条对局路径。三个预算交错并轮换执行顺序，使用相同独立搜索随机源。JIT 预热不进入计时，候选合法性与信息一致性在计时后校验。

分别比较默认预算、已有快速预算和提议的交互预算（8/64、80 ms）；再对第一副的 48 次决策单独插桩，分解 DP 建立、采样、模拟、残局和策略成本。模拟/残局耗时包含其中的策略耗时，不能再次相加。

本基准测量 Node 搜索内核；不包含 Worker 启动和传输、浏览器冷启动、显示等待或绘制。出牌一致率仅用于观察预算改变的影响，不代表赢副率。

### 本次实测

本机为 macOS ARM64，Node v26.3.0；完整基准通过，运行约 79 秒。

| 预算 | 全部决策平均 / P50 / P95 | 需要搜索的决策 P50 / P95 | 与默认出牌一致率 |
| --- | --- | --- | --- |
| 默认：16/1024，250 ms | 137.25 / 218.76 / 250.06 ms | 250.05 / 250.06 ms | 100% |
| 已有快速：8/32，120 ms | 19.47 / 9.06 / 84.85 ms | 22.11 / 94.92 ms | 82.6% |
| 提议交互：8/64，80 ms | 28.46 / 16.61 / 80.05 ms | 44.17 / 80.06 ms | 86.2% |

384 次观察中，87 次仅有一张合法牌、53 次胜负已锁定，244 次需要进一步搜索。三个预算均未出现 `fallback` 或 `inconsistent`。已有快速预算平均计算成本更低；8/64 的平均成本较高，但尾延迟较低。不能只比较时间上限判断哪个方案更快。

首次对局单独插桩的热点如下：

| 阶段 | 合计耗时 | 占插桩总耗时 |
| --- | --- | --- |
| 全部决策 | 6047.19 ms | 100% |
| 后续模拟，含策略 | 5872.08 ms | 97.1% |
| 出牌策略，已包含在模拟等阶段中 | 5547.68 ms | 91.7% |
| 暗牌采样 | 121.15 ms | 2.0% |
| 信念 DP 建立 | 13.89 ms | 0.23% |

这支持优先优化 `observationPolicy` 的重复扫描和分配；本次第一副残局尝试几乎没有成本，不能据此推断所有小残局都很便宜。插桩调用计时本身有开销，比例用于热点定位，不代表精确生产 CPU 占用。

以上 82.6%/86.2% 的一致率包含强制跟牌和胜负已锁定的局面，不能用来推断胜率下降多少。此前 32 样本对快速启发式的实验也不能证明它与当前默认 1024 上限预算的棋力等价。

## 4. 实施顺序

### P0：先缩短牌桌等待，补齐完整请求耗时

1. 将正常显示等待从 650 ms 调到约 240–300 ms，快速先保留约 180–220 ms，慢速保留用户偏好的阅读节奏。最终值以浏览器及移动设备实测确定。
2. 将速度对应预算放在浏览器组合配置中。优先接入已有 `FAST_OPTIMIZED_BUDGET` 做试验；8/64、80 ms 为待验证选项，不直接当作已通过棋力验收的默认值。
3. 在 Worker 客户端直接处理唯一合法牌。已有获胜锁定的局面可直接采用相同合法兜底策略，不启动 Worker；保留规则、取消和合法性校验。
4. 记录客户端请求起止、Worker 内部 `elapsedMs`、最终应用/绘制时刻、状态、完成样本数和兜底原因。区分内核耗时、Worker 往返耗时和人为等待。当前 Agent 只取 `decision.card`，诊断信息没有上报。

如果请求能在新的显示窗口内完成，三个 AI 连续行动的显示下限可从 1.95 秒降到约 0.72–0.90 秒。这是配置计算出的目标，尚非浏览器实测结果。

### P1：复用 Worker 与保持策略等价的热点优化

1. 每个牌桌保留一个 Worker，串行接收各 AI 座位的请求；成功后保持空闲。仅在取消正在运行的搜索、执行失败、超时或牌桌卸载时终止并按需重建。
2. 保留递增请求编号、过期结果保护和 `AbortSignal`。搜索本体同步运行时，单发一条取消消息不能立即打断它；取消活动请求仍需 `terminate()`。
3. 按公共出牌维护 52 张牌的已出掩码。每个模拟玩家的未知牌集合由公共记录、该玩家手牌及其有权知道的底牌生成，防止不同座位的私有信息互相泄露。
4. 每次策略调用先建立各花色未知牌数量、比某张牌更大的数量、后手敌人可持有牌及压牌风险；候选共享这些结果，替代候选循环内重复的 `filter`、`Set`、`Map` 创建。相同赢家的风险也可以在该次调用内复用。
5. 预计算 52 张牌的 ID、花色、点数和大小；模拟内部逐步减少字符串拼接、临时数组与对象分配。改动先保持原策略打分、浮点运算和同分顺序一致。

P1 的目标是在相同样本和后续策略下减少计算成本；更多可完成样本可能改变限时搜索结果，因此仍需实际对战验证。

### P2：减少无法完成的计算，再调预算

1. 保留全候选共用样本及预定检查点。估计最近一段每个完整样本成本，若下一检查点明显无法在剩余预算内完成，直接返回已经提交的结果，减少超时后整体丢弃的工作。
2. 监测前几轮的 `fallback` 比例。若设备无法完成 8 个共同热身样本，再试验 4 个样本的首检查点；同步更新联合误差分配。不要只缩短时间而导致多数决策退回启发式。
3. 按候选数、剩余轮次和已完成样本的吞吐分配计算，使用固定总截止时间。强制跟牌无需搜索，复杂领出多分配预算，接近获胜线时保留必要计算。
4. 首轮保留全部合法牌。启发式排序用于兜底和评估顺序；不要未经反例验证就硬删除“看起来差”的牌，也不要把启发式确信等同于规则保证。

暂不优先改写 DP、改用 Rust/WASM 或增加并行 Worker。先验证模拟热点与 Worker 复用的收益；统计判据变更另做独立实验，不通过直接放宽错误概率换速度。

## 5. 验收与上线门槛

| 项目 | 验收方式 |
| --- | --- |
| 正确性 | 原有规则、暗牌隔离、模拟器一致性、配对统计、残局和取消测试继续通过。对保持策略等价的优化，固定观察和随机流比较逐步动作及评价结果。 |
| 完整体验 | 桌面正常模式目标 P95 ≤300 ms/张，快速 ≤220 ms/张；浏览器分别记录首次请求与后续请求，包含 Worker、显示等待和绘制。目标尚未实测达成。 |
| 移动设备 | 至少一个实际低性能移动设备测同一语料，记录 P50/P95/最大值、热身失败率和取消响应，再决定设备预算。Node 数字不外推为手机承诺。 |
| 计算收益 | 分别比较基线、只调节奏、只复用 Worker、只优化策略、再缩预算，定位每项收益。完成样本数与丢弃工作量一起报告。 |
| 棋力 | 固定叫分/定主/扣底，旧默认预算与候选配置按同一发牌交换双方，至少 2000 个独立发牌组，按组计算配对赢副率差的 95% 区间。建议验收下界不低于 −2 个百分点；区间太宽则增加组数。另覆盖不同叫分与更多对手策略。 |
| 生命周期 | 成功请求复用 Worker；重开、切速度、换副、取消、执行失败和卸载不应用旧动作、不遗留活动 Worker。 |

推荐推进路径：**P0 节奏和观测 → P1 Worker 复用及策略热点 → P2 自适应预算 → 完整延迟与棋力联合验收**。
