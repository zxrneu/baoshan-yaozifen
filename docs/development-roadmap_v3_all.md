# 开发路线图 v3 — 后续规划（产品化 · 训练 · 在线 · 分发）

> 更新日期：2026-10-12 · 本文保留产品化、训练、在线与分发的后续候选，不替代当前执行清单。
>
> **当前优先级以 [开发路线 v2.1](development-roadmap.md) 为准**：P0 SQLite 历史 → P1 复盘 → P2 多 LLM/System One 与算法参数配置 → P3 HTTP 模拟对战。详细契约见 [专项设计](game-history-replay-and-engine-profiles.md)。这些基础功能不等待 M0–M3 的牌力实验，也不等待在线服务或训练语料管线。
>
> M0–M4 / A0.x–A4.x 保留为配套研究编号；本文 V3-x 只补后续范围。旧“先完成 M0/M1，再考虑所有历史/产品能力”的顺序已被当前 P0–P3 替代。

## 1. v3 的四个方向与依赖关系

当前基础工具主线：P0 SQLite 历史 → P1 复盘 → P2 多配置引擎 → P3 模拟与报告。

完成基础闭环后，按需求展开产品化、在线与分发；训练研究仍按 M4 的数据/教师/算力前置推进。M0–M3 用于模拟的可信统计与牌力改进，不作为保存原局和回放动作的前置。

**与 v2.0 的关系（关键）**：

- **RL 不单独提前**。v2.0 已把 RL 放进 **M4**，并明确"**不预设 RL 必然超过搜索**"，且 M4 要求先做**受控监督/蒸馏**（A4.2）、蒸馏不足且算力明确后才做自博弈 RL（A4.3）。本文 §2 只补 M4 的**成本量级与外部参照**，不另立并行计划。
- **当前历史、复盘和多配置模拟按 P0–P3 先交付**；其余整批产品改造后置按需求立项。牌力排序和默认引擎替换仍要求独立评测，不能把它当作历史功能的前置。
- **在线对战（V3-3）与分发（V3-4）可先小步做**，因为它们**不依赖 AI 强度**：Web 端发布成本极低，且能带来真实对局数据（反哺 M4）。

## 2. 关于 RL 的现实参照（补 M4 决策依据）

v2.0 A4.1–A4.4 已给出正确的**顺序**（先语料 → 再蒸馏 → 蒸馏不足才 RL）。本节补的是**成本量级**，供 M4 放行决策使用。

参考 [PerfectDou](https://arxiv.org/html/2203.16406v7)（斗地主 SOTA，同属"跟牌 + 吃分"家族）的公开数据：

| 项目 | PerfectDou (DouDizhu) | 对保山幺子分的含义 |
|---|---|---|
| 训练步数 | **2.5e9 steps** 才超过 DouZero | 即便规模缩小仍是**亿级**；是 GPU 机时问题 |
| 动作空间 | 原始 27472 → 抽象到 621 | 幺子分跟门规则动作空间**更小**（同门必跟），有结构优势 |
| 对手基线 | DouZero 约 1e10 steps | 我方最强 `bridge-deep` 是**搜索式**，非学习式，对照关系不同 |
| 网络结构 | LSTM + MLP，策略 [256,256,256,512] | 规模不大，**推理成本可控**（利好在线部署） |
| 训练范式 | PPO + GAE + 完美信息蒸馏 (PTIE) + **分布式 rollout** | 分布式是**必需项**，不是优化项 |
| 理论保证 | **三人博弈无收敛性证明** | 幺子分是**四人两方**（更接近二人零和），但**未验证**，不可假定 |
| 人类对照 | 对人类高手 WP 0.625 / ADP 0.590 | 达到此水平才有产品说服力 |

**结论（供 M4 放行参考）**：
1. RL 的对手是"**搜索式引擎**"，不是论文里的"学习式引擎"。搜索式在残局可逼近精确解，RL 未必占优 —— 这必须在 M2/M3 用数据回答，不能靠类比。
2. A4.2 的**蒸馏**是性价比最高的一步（教师已通过实战确认，无需探索）：它直接复用 M0–M3 积累的轨迹语料。
3. **算力是硬门禁**：当前仓库无任何训练脚手架。M4 放行前须先明确 GPU 环境与预算，否则 A4.3 无法启动。
4. 信息隔离是**硬约束**：A4.3 的非对称 Critic 可用全局信息，但 Actor 与推理**只能**走现有 `observeDecision` 白名单（`src/ai/decisionObservation.ts`），**不得为训练方便开洞**。

## 3. V3-1 产品化（B 轨道整批立项）

v2.0 轨道 B 的 B1–B7 是**逐项候选**，且"须通过具体场景复现"。本文补的是：**什么时候把 B 整批立项，以及立项后的形态**。

**准入条件**：有明确玩家需求与具体验收，再决定是否集中推进后置体验项；历史、复盘和多配置模拟已有当前授权，按 P0–P3 推进。涉及“更强”宣传或默认替换时才要求独立牌力确认。

**V3-1a · B1–B7 收口**：按 v2.0 既有验收逐项关闭。注意 B1（小屏）是 V3-4 移动分发的**前置**。

**V3-1b · 局外留存（B7 展开）**：战绩、成就、连胜等积累感。**前置**：P0 SQLite 历史库交付，并具备可查询的对局结果。
- **验收**：有局外可见的积累感，具体形态待 P0 后细化

**V3-1c · 内容与传播（对应 v2.0 远期 G6）**：30 秒玩法动图、四引擎对比图、技术博客。地方棋牌（保山/腾冲）有地域话题，是冷启动切入点。
- **验收**：有可分享的对外材料

## 4. V3-3 多人在线

**现状：零代码。** 无 WebSocket / socket.io / webrtc / room 实现；`server/proxy.ts` 只代理模型调用。

### 4.1 架构决策（先定这个，再写代码）

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **A. 权威服务端 + WebSocket** | 规则单一权威、防作弊、易观战/回放 | 需常驻服务与运维 | **推荐** |
| B. P2P / WebRTC（host-authoritative） | 无服务器成本、低延迟 | 作弊易、断线难处理、NAT 穿透复杂 | 不推荐：四人两方暗牌价值高 |
| C. 纯 HTTP 轮询 | 实现最简 | 实时性差、移动端耗电 | 不推荐 |

**推荐 A 的理由**：四人两方是**合作博弈**，暗牌信息价值高 → 防作弊是硬需求；且已有 `server/` 基础设施可扩展。

### 4.2 任务分解

**V3-3a · 对局服务骨架**
- 在 `server/` 下新增房间/对局服务（与模型代理**职责分离**）
- 服务端持有权威 `GameState`；客户端只发意图、只收本座位可见观察
- **关键约束**：复用 `src/ai/decisionObservation.ts` 的白名单投影 —— **信息隔离在服务端同样必须成立**，不能让客户端拿到全局状态
- **验收**：客户端抓包**无法**看到其他座位暗牌、未知底牌、发牌 seed（安全红线，必须有自动化测试）

**V3-3b · 断线重连与超时托管**
- 四人实时游戏，断线是常态而非异常
- 玩家超时 → 临时交由 AI 托管（复用现有引擎），回来可接管
- **验收**：拔网线重连后状态一致；超时玩家由 AI 出牌且不阻塞他人

**V3-3c · 匹配与房间**：好友房（邀请码）+ 快速匹配
- **验收**：4 人可组局开打完整一副

**V3-3d · 观战与回放**：复用 P0 历史库与 P1 复盘；回放本身是**教学素材**（呼应 B5）
- **验收**：任意已结束对局可回放

### 4.3 与 AI 的关系
- 座位不足时用 AI 补位 —— 这是**冷启动关键**，不必凑满 4 个真人
- 在线场景下 AI 强度不如**速度**重要：不能等 30 秒（当前 LLM 扣底 P50 达 1050 秒级，见 v2.0 §1）

## 5. V3-4 三端分发

**现状**：Tauri 2.12.1 已配置（`productName` 保山幺子分，1024×720，`minWidth: 800`），仅生成 `gen/android`，**无 iOS/桌面产物**；权限仅 `core:default` + `opener:default`，**无网络权限**。

**优先级建议：Web（最省）→ Android（已就绪）→ 桌面 → iOS（最贵）**。iOS 的开发者账号与审核周期是真实成本，不应排在最前。

**V3-4a · Web 端发布**（可最早做，无硬性前置）
- 现有 Vite 产物即可部署，**成本最低的分发渠道**
- 注意：LLM 引擎需要模型服务，Web 端要么自带 API Key 要么走 `server/proxy.ts`
- **验收**：公网可访问，核心玩法可用

**V3-4b · Android 打包**
- `gen/android` 已存在，补签名、图标、版本号
- **前置：B1 小屏裁切完成**（否则移动端装上也用不了）
- **验收**：产出可安装 APK/AAB，真机安装可玩

**V3-4c · 窗口约束与小屏对齐**
- `src-tauri/tauri.conf.json` 的 `minWidth: 800` / `minHeight: 600` 与 B1 直接冲突：手机竖屏普遍 375–430 宽
- **必须先完成 B1** 再调窗口约束
- **验收**：真机（Android + iOS 各一台）竖屏可完整操作

**V3-4d · 桌面分发**
- Tauri `targets: "all"`，可出 macOS/Windows/Linux 包
- **验收**：至少 macOS + Windows 安装包可用

**V3-4e · iOS 打包**
- 无 `gen/ios`，需 `tauri ios init`；需 macOS + Apple 开发者账号
- **注意**：iOS 对本地模型调用限制更严，**LLM 引擎在 iOS 上大概率不可用**，须回退 `bridge-fast`（已有优雅降级链路）
- **风险**：棋牌类应用在部分地区审核敏感，可能被拒
- **验收**：TestFlight 可安装

## 6. V3-2 数据飞轮

**定位**：P0 已负责 SQLite 对局保存，P1 负责复盘；本节只补后续真实对局诊断与 A4.1 训练语料，不重复建设历史库。

**V3-2a · 后续远端统计采集**（独立于本地 SQLite 历史）
- **隐私边界**：匿名、可关闭、不采集个人信息 —— 必须在**实现前定稿**，不能事后补
- **验收**：对局数据可导出；隐私开关生效

**V3-2b · 真实对局用于诊断**（不直接训练）
- 人类对局是**分布外样本** —— AI 自博弈不会走出的局面，恰是 AI 盲区
- 做法：把人类对局作为**回归测试集**与**启发式调优输入**（先诊断，不直接训练）
- **验收**：产出 AI 决策异常榜单（人类一致选择 vs AI 选择分歧最大的局面）

**V3-2c · 训练语料管道**（并入 A4.1，不另立）
- v2.0 A4.1 已定义语料字段、划分与去重规则；V3-2c 只负责把**真实对局**作为来源之一接入
- **验收**：数据管道可复现（固定种子 + 版本化），来源与质量标签齐全

## 7. 成本与风险清单

| 项目 | 成本量级 | 风险 |
|---|---|---|
| RL 训练（M4） | **GPU 机时**，参照 2.5e9 steps | 收敛不确定；论文对三人博弈**无收敛保证**；我方对照物是搜索式引擎，**RL 未必占优** |
| 在线对战 | 常驻服务器 + 运维 + 反作弊 | 冷启动：没玩家就没有对局，没对局就留不住玩家 |
| iOS 分发 | Apple 开发者账号年费 + 审核周期 | 棋牌类审核敏感，可能被拒 |
| LLM 引擎 | 每次决策一次推理；扣底 P50 达 1050 秒级 | 上线前必须先解决延迟与成本（v2.0 M0–M2） |
| 数据采集 | 存储 + 合规 | 隐私合规是**法律问题**，不是技术问题 |

**最需警惕的风险**：v1 的教训是"排期骗人"；v3 的同类风险是"**为了做 RL 而做 RL**"。v2.0 已写明"不预设 RL 必然超过搜索"—— 这是正确的护栏，v3 不推翻它。

## 9. 建议的推进顺序

当前首先按主路线交付 **P0 历史库 + P1 原路径复盘**，再交付 **P2 多配置选择/HTTP 路由 + P3 对战模拟**。配置版本与历史关系从 P0 一开始设计。

本篇候选随后按实际需求推进，Web 发布、在线房间、正式跨端分发不作为本地 SQLite 历史的前置。模型预算/故障归因配合 P2/P3；更大牌力实验和训练继续遵守主路线 M0–M4 的证据边界。

本地 SQLite 保存供本人使用的对局，不因此引入账号、匿名统计或远端采集。后续若增加远端统计，在该功能范围内明确记录字段与开关。
