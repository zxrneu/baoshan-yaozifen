## 目录与单一职责

| 位置 | 维护什么 | 避免重复 |
| --- | --- | --- |
| 根 `README.md` | 项目介绍、最短启动、关键能力与入口 | 不维护完整资料列表、固定测试数和详细研究方案 |
| 根 `TODO.md` | 近期候选导航 | 不复制完成清单、状态表和研究全文 |
| `docs/README.md` | 全文档导航与使用边界 | 不维护第二份协议或排行榜 |
| `guides/` | 玩法、玩家操作和开发命令 | 详细协议链接到功能/源码 |
| `features/`、`architecture/` | 当前行为、契约、边界及代码落点 | 接口字段以源码为准；历史验证需标日期 |
| `ai/` | 评测方法、可复现记录、策略分析与搜索实现 | 旧套件结果独立标识，不混排当前成绩 |
| `design/` | 目标、交互、设计取舍和候选 | 设计不证明交付；实现状态回链功能/路线 |
| `planning/` | 路线维护状态/顺序，研究文档维护验收，后续文档维护候选 | 不用文件名 v2/v3 形成并行执行清单 |
| `archive/` | 冻结的旧计划、设计和验证 | 原数字不替换为今天的数据，开头链接替代入口 |
| `maintenance/`、`skills/` | 文档/Git 约定、工具恢复与项目技能源码 | 本机安装副本不当作仓库源码入口 |
| `ui/`、`examples/` | 原型、截图与示例证据 | 不移动运行时/测试引用的资源路径来配合文字分类 |

## 事实来源与更新规则

1. 规则与实现以源码为准；环境、脚本和 CI 以 `package.json`、`tsconfig.json`、工作流为准。文档给解释和导航，尽量引用定义，避免抄写整套接口。
2. 任务状态与近批顺序只在[开发路线](../planning/development-roadmap.md)汇总。功能文档描述已有行为；设计与研究文档描述目标和验收，不另维护相反的执行队列。
3. 主要说明标明类型、复核日期或证据日期、使用边界，并从索引可达。历史记录明确所用版本、配置、样本和适用范围；已有文档可以同时有当前模块说明与标日期的历史验证。
4. 行为交付同时更新相关功能、路线及必要的索引链接。文档迁移保留必要历史内容，更新所有入链、图片和源码注释；不留下同主题两份“当前”说明。
5. 评测结论引用固定 run / manifest / 原始日志。根汇总允许继续覆盖，但只作为最近输出；它的名字不能充当历史证据身份。缺字段写未采集，套件/配置/源码不同不合并排名。
6. 新文档先判断能否并入现有主题，确有独立职责再建文件并登记索引。被替代的设计移入归档，注明替代入口；原型、截图、模型接入与单副冒烟分别标明验证范围。

源码指纹按完整文件内容计算，注释改动也可能影响已有模拟的续跑兼容性。因此保留旧评测方案与 P0 路径的跳转页，源码注释不变。已安装的本机评测技能还引用旧路线、结果与 P3 路径，一并保留跳转；五个兼容入口见[索引](../README.md)。这些页不复制字段、状态或成绩。技能源码使用从项目根定位的引用，确保复制到 `.agents/skills/` 后路径仍有效；本次没有改动本机安装目录。

```bash
git diff --check

```

迁移时另遍历仓库 Markdown 的相对链接、图片路径和本地标题锚点，排除示例代码块，并检查没有失效的旧路径或 `file://` 本机链接。源码注释、技能源码、评测产物索引和归档文档都属于入链范围；历史正文中的旧路径可保留作追溯，但需有明确归档说明。外部网站是否可访问不由本地链接检查保证，引用外部事实时按任务需要核验。
