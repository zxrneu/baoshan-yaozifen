# UI 布局与交互规范

本文记录本项目的界面约束。修改 UI 前先阅读，交付前按本文检查；规则与信息隔离仍以 `AGENTS.md`、引擎代码为准。

## 信息优先，减少切换

- 用户应能直接看到当前行动者、阶段、主牌与合同、双方吃分、当前决策及最近记录。
- 利用左右留白，桌面端采用「正方形牌桌 + 右侧信息区」。牌桌放牌、座位和必要的行动控件；辅助说明、状态文字、诊断和记录放右侧。
- 不用大面积空白、口号或重复提示占据信息区。战况、工具和记录铺满信息区宽度，相关指标紧凑并排，长内容在各自区域滚动。
- 动画期间的战况、行动座位与牌桌都读取当前展示步骤，不提前呈现后续分数或下一位玩家。
- 同一信息只有一个常驻展示来源：主牌、叫分与目标线由战况展示，当前行动仅展示运行状态、行动者与对应引擎。
- Debug 的思维推演、候选走法、历史追溯直接展示，禁止用 Tab 隐藏这些常用信息；历史结论和理由无需点击展开。
- 常用诊断区至少在初始桌面布局中同时露出标题和内容入口；不能只是移除 Tab，却把历史区排到首屏之外。宽度允许时并排排列，避免网格留下空列。
- Debug 已能查看四家手牌，不再提供「绝门记牌」这类重复推断面板。
- 普通对局和观战也直接展示公开战况、行动状态和记录，避免把常用信息全部藏在弹窗中。

## 引擎配置只有一个来源

- 每个座位使用自己已分配的引擎配置。Debug「下一步」沿用当前行动座位配置，不另设工作台全局引擎选择器。
- 当前行动的引擎与已执行决策的实际引擎分别准确标注，不能用全局默认引擎或下一位玩家的引擎冒充历史结果。
- 玩家与引擎只通过牌桌上各家引擎名称逐座设置。设置弹窗不提供两队批量配置或统一打法入口，避免覆盖独立配置。
- Debug 看牌只改变 UI；不得改变 AI 观察对象的合法信息范围。

## 操作紧凑且含义明确

- 单步推进只有一个主入口「下一步」，保留空格快捷键。按钮采用紧凑尺寸，不做横贯整个面板的大横幅。
- 常驻操作保留建议、撤销、恢复和决策日志；音效等全局控件不在工作台重复。
- 普通对局和 Debug 的叫分、定主、扣底、出牌确认集中在右侧；普通、Debug、观战的动作说明与展示推进也在右侧正向阅读。手机横屏保留右侧操作区，避免操作与手牌互相遮挡。
- 普通、Debug、观战和练习打开后均暂停；切换模式、重开或人工单步操作不得隐式启动自动对局。顶栏统一提供一个「开始／暂停」按钮，单步仍独立可用。
- 种子和快照放在主要信息之后；不得在沙盒或观战面板重复开始／暂停控件。
- 鼠标点击动画下一步与空格遵循同一单步语义：先暂停，再推进一项；不能点了一步却继续自动连打。
- 切换「开始／暂停」保留同一局面的人工出牌和扣底选择；改变局面、座位配置或重新开局仍清除过期选择。
- 明确区分「只评估」「执行动作」「恢复已记录动作」；等待、失败和结束状态给出准确反馈。

## 牌面与正方形牌桌

- 桌面端普通对局、Debug 和观战使用正方形牌桌，按可用高度确定边长，剩余宽度用于信息区。
- 四个座位及手牌位置明确，牌张排列和旋转不能挤压中央出牌区域。
- 每张牌的中央花色在几何中心，图形不倾斜、不使用随字体变化的偏移补偿。
- 点数、角上花色、分值、主牌和底牌标识各有空间；任何尺寸和座位旋转下都不得互相覆盖。
- 桌面普通手牌优先排列为一行，利用实际手牌区宽度；扣底与触屏保留独立可点击的完整牌位；触屏不沿用鼠标叠牌，每张牌的点击区域不相交，动作推进按钮至少 44×44px。叠牌后可见部分仍能辨认点数和花色。检查 `10`、A、5、主牌和底牌组合，不能只检查没有角标的牌。
- 手机等矮屏允许适应首屏操作的布局；不得为强求正方形而把手牌和主操作挤出视口或缩成难以点击的尺寸。

## 侧边弹窗与遮挡边界

- 设置、规则、决策理由、查看牌张、历史、结算等弹窗统一进入侧边信息区，不在牌桌中央覆盖四家手牌。
- 所有弹窗复用 `Modal` 的停靠外框；自定义外观（包括摸底揭晓）也必须保留统一外框类，不能绕过停靠规则。
- 弹窗占用预留的信息栏空间；打开后四家牌面的矩形不得与弹窗相交。不能仅把居中遮罩改为靠右却仍压住手牌。
- 不给整个牌桌加模糊或不透明遮罩；查看弹窗时统一暂停对局，关闭后保持暂停，等待明确点击「开始」。弹窗打开期间隔离牌桌和顶栏的鼠标、触屏与键盘输入，同时保留牌面可见；多层弹窗逐层恢复输入，方向提示保持可访问。
- 动作说明和其他临时浮层也应遵守手牌安全边界。必要的出牌动画可在桌面展示，但不能覆盖角上的点数。
- 窄屏采用侧边或牌桌之后的可滚动布局，保证原局仍可查看；不通过整体缩放牺牲可读性。
- 弹窗统一挂载到牌桌的侧栏停靠区域，不能嵌入顶栏等会裁剪内容的容器。保留焦点管理、Escape 关闭、明确关闭按钮和焦点返回。长内容在面板内滚动，不让关闭或主要操作消失。

## 交付检查

1. 新交互或修复先写回归测试并确认目标失败，再实现；纯样式不制造无意义失败测试。
2. 用真实浏览器检查 1920×1080、1280×720 桌面和手机横屏，至少覆盖普通对局、Debug、观战及打开侧边弹窗。
3. 实测牌桌宽高、弹窗与手牌是否相交，以及中央花色与角标是否重叠；视觉问题不能仅凭构建通过判断。
4. 确认信息无需切换即可读取，控件没有重复，引擎显示与实际执行一致。
5. 按项目要求跑通 `pnpm test` 与 `pnpm build`，报告无法完成的验证及原因。
