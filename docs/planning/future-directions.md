## 多人在线（V3-3 / T3.3）

2026-10-15 用户选择熟人约局、P2P 与低服务器成本优先。详细候选见[熟人 P2P 联机与 Monorepo 演进](multiplayer-and-monorepo.md)：首版由可信房主持有权威牌局，WebRTC 直连、WSS 信令与中继兜底；大厅与牌局权威分开，房主掉线先暂停/恢复，无法恢复则中止本副。

公开房后续采用权威服务端 + 实时连接：服务端持有规则状态，客户端只发送意图、接收本座位合法可见信息。当前决策服务校验观察，但不具备独立权威牌局，需新增房间与对局服务；熟人房的房主裁判结果不直接作为可信积分依据。

按房间/身份与消息协议 → 对局状态投影 → 超时托管与断线恢复 → 观战与历史集成逐项定义验收。抓包和自动测试须证明看不到其他暗牌、未知底牌及 seed；沿用阶段观察边界，不把现有全局快照直接广播。在线托管需声明端到端预算与失败策略，使用目标环境实测。

## 分发（V3-4 / T3.4）

Web、Android、桌面和 iOS 分别按需求与工具链验收，不固定平台顺序或发布工期。打包方法见[开发指南](../guides/development.md)。目标端需验证布局、网络/本地引擎、历史可用性、签名与更新流程；无 Node 服务的 Tauri 原生历史适配单独立项，复用现有 Repository 契约。

## 数据、训练与规则演进

V3-2 的真实对局诊断复用现有历史与复盘，先生成可复现的异常样本。训练语料并入 A4.1，按整副牌划分、来源/质量标注与去重；Mock、失败、未评估及低质量标签单列。

RL（T3.2 / M4）遵循[研究规格](ai-research.md#m4--基于证据决定是否训练)：先语料治理、可靠教师蒸馏，确认不足且算力/预算明确后再考虑自博弈。Actor 只用合法观察，非对称 Critic 的全局信息不进入推理；接入仍经同协议整副评测，不预设训练胜过搜索。

规则变体（T3.1）需独立规则标识、数据与回归。对手预计算（G2）仍为候选：公开动作会改变观察，可预热服务或缓存合法特征，不能保证当前建议在下一轮仍有效。
