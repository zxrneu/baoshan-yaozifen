# Phase 0 · 质量底线（P0，先修 Bug）

> 原则：**先止血再谈体验**。这些问题要么让"深度思考"名不副实，要么留下非法兜底契约，属于上线前必修。
>
> **进度**：T0.1 ✅ 已完成；T0.2 / T0.3 / T0.4 ⏳ 待办。详见 [§1.1 完成记录](#11-完成记录)。

## T0.1 修复扣底极端兜底扣回分牌 ✅ 已完成（2026-10-12）

> **状态**：已修复并验收，详见 [§1.1 完成记录](#11-完成记录)。
> **严重度修正**：下面的"对局卡死"结论经实测不成立——全副仅 12 张分牌 / 40 张非分牌，任意 16 张中非分牌最少 6 张，该局面在任何合法发牌下不可达。它是一处**潜伏缺陷（非法兜底契约）**，不是线上卡死。修复价值在于 `buryFromObservation` 是公开导出函数并被四个引擎共用作兜底。
> **实际改动**：兜底仍只在非分牌中选取（`src/ai/smart.ts`、`src/ai/heuristic.ts`）；非分牌不足时显式降级为"不足数"并告警一次。回归测试 `tests/extreme-bury.test.ts`（8 用例）。采用"降级 + 告警"而非"抛清晰错误"，因为 LLM 引擎把该函数当作模型失败时的安全网，抛错会击穿安全网。

- **位置**：`src/ai/smart.ts` `buryFromObservation`、`src/ai/heuristic.ts` `aiBury`
- **问题**：当庄家手牌分牌（A/10/5）≥9 张、非分牌不足 4 张时，兜底逻辑从全手牌取点数最小的 4 张，**未排除分牌**，违反"分牌不能扣底"规则。
- **复现**：构造 9 分 + 3 非分手牌 → `buryFromObservation` 返回 `KS 5H QC JC`（含 1 张分牌 `5H`），`engine.bury` 抛 `IllegalActionError`（该座位将无法扣底）。**但该局面在合法发牌下不可达**，详见上方严重度修正。
- **方案**：兜底也仅在**非分牌**中选；若真无解（理论上极罕见），显式降级为"不扣够数并告警"或抛清晰错误，绝不返回含分牌的非法动作。
- **难度**：低（1–2h）。**验收**：构造 ≥9 分牌手牌，扣底不抛错、不含分牌；新增回归测试 `extreme-bury.test.ts`。

## T0.2 修正提前结算阈值 105−B → 101−B

- **位置**：`src/engine/game.ts:266`、`src/ai/bridge/dds.ts:115`、`README.md`、`TODO.md`
- **问题**：当前用"闲家达到 `105−B` 立即结束/截断"。数学上闲家必胜阈值为 **`101−B`**（总副分 100，庄家方最大 = 100−闲家吃分；闲家必胜 ⟺ 100−D < B ⟺ D ≥ 101−B）。
- **影响**：不产生错误结算，但阈值偏保守 4 分 → 闲家已锁定胜局仍空打、DDS 剪枝效率略损、README 公式声明错误。
- **注意**：`105−B > 101−B`，把 DDS 截断提前到 `101−B` 仍安全（该点是严格锁定下界，继续搜结果相同）。改后**必须重跑 `bridge-dds.test.ts` / `bridge-engine.test.ts`** 确认 `moveScores` 不变。
- **难度**：低（0.5–1h）。**验收**：新增参数化测试覆盖 B∈{70…100} 的 `101−B` 边界；README/TODO 公式同步更新。

## T0.3 修复 PIMC 唯一候选指标失真

- **位置**：`src/ai/bridge/pimc.ts:77-86`
- **问题**：唯一候选直接出牌时返回 `winRate: 1, expectedPoints: 0`，把"被迫出牌"标成"必胜"。
- **影响**：决策日志、胜率统计、`docs/examples` 指标系统性污染，误导后续 RL 基线对比。
- **方案**：唯一候选返回 `winRate` 置为合理基线（或标注 `forced` 状态），不伪装成 100% 胜率。
- **难度**：低（0.5h）。**验收**：决策日志不再把被迫出牌记为 100% 胜率。

## T0.4 PIMC 跟牌退化（本次最高优先级算法缺陷）

- **位置**：`src/ai/bridge/bridgeEngine.ts` `chooseCard` + `src/ai/bridge/pimc.ts:136-144`
- **问题**：`BridgeEngine.chooseCard` 在**跟牌**（非领出）时也调用 PIMC，而 `pimc.ts` 用 `observation.leader` 作为 DDS 求解对象且 DDS 内部 `currentTrick` 初始为空——**忽略当前轮已出的牌，且求解的是 leader 而非当前玩家**。
- **复现**（运行时已证实）：跟牌局面（决策者第 3 家、候选 6C/JC/QC）→ 三个候选 `samples=0、winRate=0.5、expPts=50`，最终靠专家规则兜底。
- **影响**：默认引擎（bridge）在**每一次跟牌决策上 DDS 全部空转**，"深度思考"名不副实。
- **方案（建议分两步）**：
  - **T0.4a（止血，2h）**：`BridgeEngine.chooseCard` 增加分支——`observation.currentRound.length > 0`（跟牌）时直接走 `evaluateBridgeTactics`，不走 PIMC。改动最小、立竿见影，消除空转。
  - **T0.4b（增强，P1）**：扩展 `DoubleDummySolver.solve` 接口接收当前轮已出牌，让 PIMC 在跟牌时也做完整 DDS 推演，让跟牌同样获得深度思考。收益高但需改 DDS 契约 + 测试。
- **难度**：中（止血 2h；增强另行排期）。**验收**：跟牌候选 `samples>0` 或明确走 tactics；无空转 DDS；新增跟牌回归测试。

# Phase 1 · 产品重塑（P1，从"开发者自嗨"回到"玩家视角"）

> 原则：**把开发者功能收走，把玩家体验补齐**。这个阶段的价值是"把能打的引擎，变成有人愿意玩的游戏"。

## T1.1 出牌交互统一为"点牌即出"

- **位置**：`src/hooks/useGame.ts` `onCardClick`、`src/components/HumanHand.tsx`、`ControlPanel.tsx` `PlayPanel`
- **问题**：出牌存在三条并存路径——"点牌选中→点『出牌』按钮确认"、"再点同一张牌直接出"、"键盘空格/回车"。棋牌是高节奏强肌肉记忆场景，**操作模型不统一会让玩家无法形成稳定预期**，且移动端键盘快捷键全部失效。
- **方案**：默认"**点牌即出**"（点不同牌=换牌、点同牌=取消或出，可按配置）；移除/弱化独立"出牌"按钮；移动端加大出牌热区、支持双击出牌。可加"出牌二次确认"开关（新手默认开、老手关）防误触。
- **难度**：中（1–2h）。**验收**：一套交互模型覆盖全部阶段；移动端无键盘也能快速出牌。

## T1.2 开发者功能收进「设置 → 开发者选项」

- **位置**：`src/App.tsx`、`src/components/GameTools.tsx`、`EngineSettingsModal.tsx`、`DebugSidePanel.tsx`
- **问题**：顶栏正中的"🎮 切换调试模式"、工具栏的"AI 引擎 · 桥牌算法/Laya/大语言模型"、"🧠 决策日志"、"👀 全明手透视"全是工程功能；`EngineSettingsModal` 724 行塞满 vLLM/`qwen38_27b`/`openai_api_base`。普通玩家被这些淹没。
- **方案**：玩家主界面工具栏只留 **速度 / 规则 / 出牌记录 / 上一轮**；调试模式、引擎选择、决策日志、透视**收进"设置 → 开发者选项"**二级页面。工程能力保留但不再打扰玩家。
- **难度**：中（2–3h）。**验收**：普通玩家主界面无任何工程入口；开发者仍可一键进入调试。

## T1.3 移动端小屏裁切修复

- **位置**：`src/App.module.css`（`.app { max-height:100dvh; overflow:hidden }` + 牌桌 `min-height:620px` 组合）
- **问题**：整页锁定视口高且**禁止滚动**；短视口手机（如 iPhone SE 竖屏 ≈667px）上 620px 牌桌 + header + 工具栏 + 安全区会溢出被裁切，**看不到底部操作区**。
- **方案**：竖屏改**单列滚动 + 底部粘性操作区**（出牌/叫分按钮悬浮底部）；工具栏由横向一排改为 **icon + 短标签网格**；放宽 `overflow` 策略并保留 `safe-area-inset`。
- **难度**：中（2–3h）。**验收**：iPhone SE 竖屏、横屏、Android 小屏全流程可达、无裁切、操作区常驻。

## T1.4 AI 思考暴露弱化为"等待中"

- **位置**：`src/components/OpponentSeat.tsx`（无条件渲染 `thinkingService` 气泡）
- **问题**：正常对局中对手头顶实时滚动"拔主/兑现赢张"等推理文本，破坏沉浸、术语晦涩、长文本频繁刷新成噪声。
- **方案**：正常模式只显示"等待中"脉冲；思考详情归入决策日志，想看的人自己开。
- **难度**：低（1h）。**验收**：正常对局无推理文本泄露。

## T1.5 新手教学对局 / 首次引导

- **位置**：新增 `Onboarding` 组件 + 引导状态机 + 教学 AI
- **问题**：幺子分规则复杂（叫分档位、定主、扣底禁分牌、成局条件、提前结算、100 分明牌），但首次进入**零引导**，新玩家第一局必撞墙，全靠 toast 报错被动学习。
- **方案**：首次进入弹"3 步上手"浮层（叫分→定主→扣底禁分牌）；提供可选**教学对局**——AI 每步用一句话解释为什么这么打。
- **难度**：中高（4–8h，需要内容设计 + 引导状态机）。**验收**：新用户 3 分钟内理解核心规则，首局犯错率明显下降。

## T1.6 HUD 轮次进度 + LLM 等待预期/取消

- **位置**：`src/App.tsx` HUD、`TrickArea.tsx`、`thinkingService.ts`
- **问题**：出牌进行到"第几轮/共 12 轮"只在工具栏角落显示；AI 思考（尤其 LLM 最长 8s）期间玩家不知道要等多久、能否取消。
- **方案**：HUD 加"第 N / 12 轮"；LLM 等待显示"思考中…约 Xs"+ 可跳过/取消。
- **难度**：低中（1–2h）。**验收**：玩家随时知道本副进度与等待时长。

## T1.7 重开确认 + 玩家级撤销

- **位置**：`src/App.tsx`、`ControlPanel.tsx`、`src/workbench/session.ts`
- **问题**："重新开局"直接替换对局，`undo` 仅调试模式可用（z 键）。普通玩家误点即丢整局进度。
- **方案**：重开加二次确认弹窗；或提供"本副重来"轻量撤销（对齐手牌/底牌/比分）。
- **难度**：低（0.5–1h）。**验收**：误触"重新开局"不丢局。

# Phase 2 · 工程巩固与安全（P2）

## T2.1 为 P0 修复补回归测试

- 为 T0.1/T0.2/T0.4 各补一条防回归测试（极端扣底、结算边界参数化、跟牌 PIMC）。**与对应修复同步落地**，避免缺陷复发。
- **验收**：每个 P0 修复都有独立测试套件守护。

## T2.2 魔法常数文档化/配置化

- `estimateBidStrength` 里的 `21`/`25`/`1.6`、`aiBid` 的 `1.6` 等硬编码调参，加注释或抽成集中配置，说明量纲与依据，方便后续 RL 对照。
- **难度**：低（0.5h）。**验收**：参数有据可查、可调。

## T2.3 服务端安全加固

- **位置**：`server/proxy.ts`（CORS `*`、`/api/decision` 无鉴权）
- **问题**：本地可用，但暴露公网时任意站点可调用决策服务。
- **方案**：为 `/api/decision` 加轻量 token 鉴权 + 速率限制；CORS 白名单化；静态托管补 path 校验（现基本安全，可再加固）。
- **难度**：中低（1–2h）。**验收**：公网部署时无未授权调用、无路径穿越、无 CSRF 面。

# Phase 3 · 未来演进（里程碑级）

> 这三块是大工程，建议**独立排期、单独里程碑**，不要和 P0/P1 混在一起赶。每块先立基线再动手。

## T3.1 规则完备（地方变体）

- **抠底翻倍**（末轮庄家方拿底则底牌分翻倍）：新增一个 `ScoringRule` + 末轮判定即可接入，**开闭原则天然支持**，改动小（1–2h）——但规则细节需先确认。
- **反主 / 闷牌 / "幺子"特殊牌型**：需社区/本地玩家确认规则后实现，改动中高。
- **建议**：先做抠底翻倍作为"变体接入示范"；其余列待办等社区输入。**验收**：变体可插拔，不影响 basic-v1。

## T3.2 自训强化学习（README 已规划 6 项，全部未做）

- 建议顺序：**合法动作掩码 → 团队奖励 → 自博弈联赛 → 非对称 Actor-Critic → ONNX/SafeTensors 导出 → `RlEngine` 接入 → 统一评测**（2000+ 局换位对抗，对比启发式/Worker/Laya）。
- **前置**：先修好 T0.4（PIMC 跟牌），否则 RL 会学到"跟牌时 DDS 空转"的错误信号；并用现有引擎跑一遍 2000 局基线，确定起跑线。
- **难度**：高，建议 4–6 周分段交付。**验收**：与基线对比有可量化的赢副率/净得分提升，且 `RlEngine` 走统一 `DecisionEngine` 接口可无缝替换。

## T3.3 多人在线联机

- **现状**：引擎可独立跑服务端（`server/` 无框架 http），但联机/房间系统未实现。
- **建议路径**：先做"**观战/回放**"过渡（已有 `getReplay`/快照，成本低、能验证服务端可靠性）→ 再做 WebSocket 房间 + 状态同步 + 鉴权。避免一上来就上对战导致范围失控。
- **难度**：高，分期。**验收**：稳定支持 2 人以上实时对局，断线重连可恢复。

## T3.4 三端正式分发

- **现状**：macOS 可打包；Android 走 debug APK 侧载；iOS 需付费账号签名；CI 不含签名发布。
- **建议**：补齐 CI 签名发布（Apple Developer 账号/证书为外部依赖）；Android 规范 release 签名。**验收**：三端一键分发到 TestFlight / APK / DMG。

# 5. AI 引擎效果提升与评估方案

> 聚焦：项目里四类决策引擎（**Bridge** 桥牌启发式+蒙特卡洛 / **Algorithm** 约束采样搜索 / **Laya** 非自回归小模型 / **LLM** 大模型）到底谁强、强多少、怎么提升、怎么证明提升有效。
> 核心结论：**评估先于提升**。你的 `experiments/` 已经是很好的消融设施，但目前只测"启发式/算法策略函数"，没把四类真实 `DecisionEngine` 放进同一套对打里，也没有绝对强度标尺。本文给一套完整框架。

## 一、你已有的评估设施（基础很扎实，别重复造）

`experiments/harness.ts` + `run.test.ts` 已经具备：

- 四阶段（叫分/定主/扣底/出牌）全部可注入策略的 `playHand` 对局驱动；
- `pairedDiff`（同种子跨策略**配对差分 95% CI**，消除发牌噪声）、`rateCI`、`bucketSuccess`（按牌力/分牌分层成局率）；
- `withDealer` **换位**（消除座位/叫牌顺序偏差）、`forcedBid(x)` 强制叫分、`roleSplit` **进攻/防守分开测**；
- 已有 A/B/C/D/E/F 六组实验：出牌消融（N=4000）、叫分难度曲线、定主消融、扣底消融、角色拆分、叫分策略对打；
- `decisionLogger` 记录运行中每次决策（供回放分析）。

**关键缺口**（也是这份方案要补的）：

| # | 缺口 | 后果 |
|---|---|---|
| 1 | 四类真实引擎未纳入统一对打 | `experiments` 测的是 `fastPlay/searchPlay/tacticPlay` 等**策略函数**，不是 `DecisionEngine`（bridge/algorithm/laya/llm），跨引擎强弱无结论 |
| 2 | 无跨引擎 Elo / round-robin | 无法回答"哪个引擎强、强多少、值不值得换默认" |
| 3 | 无"与理论最优差距"的绝对强度 | 现有是**相对消融**（A 比 B 好 0.5 分），依赖对手，无法度量"距最优还差多少" |
| 4 | 无分阶段独立质量指标 | 出牌被"成局率/庄分"间接度量，叫分/定主/扣底各自质量没分开量化 |
| 5 | 无模型级指标（LLM/Laya） | 延迟分布 P50/P99、非法率、重试率、超时回退率未入统一评测 |

## 二、统一评估框架（怎么评估）

### 2.1 指标分层定义

| 层 | 指标 | 含义 |
|---|---|---|
| 结果层 | 成局率、净得分、庄/闲方胜率、**Elo** | 综合强弱；Elo 用于跨引擎排序 |
| 决策层 | **出牌期望得分（副分）**、叫分准确率、定主质量、扣底质量、残局正确率 | 分阶段定位短板 |
| 运行层 | 合法率、延迟 P50/P99、超时率、回退率、重试率、决策一致性 | 工程可用性；LLM/Laya 尤其要看 P99 |
| 公平层 | 信息隔离校验通过率 | 明牌/暗牌不泄漏（沿用 `engine-fairness-isolation.test.ts`） |

### 2.2 对打协议（复用 harness，工作量最小）

1. **桥接**：为四类 `DecisionEngine` 各写一个 `DecisionEnginePolicy` 适配器，把 `chooseBid/chooseTrump/chooseBury/chooseCard` 包成 harness 的 `Policy`——这样**零改动**复用 `playHand`/`pairedDiff`/`withDealer`。
2. **Round-robin**：Bridge / Algorithm / Laya / LLM 两两对打 + 自对打，固定种子、东西/南北**换位各跑一遍**，N≥1000。
3. **基线锚点**：下限 = `random` / `min` / 出厂 `fast`；上限 = DDS 完美信息解（见 2.3）。
4. **产出**：每对组合的成局率、净得分 + 95% CI + **Elo 排行榜**（存 `experiments/results/`，延续现有 JSON 风格）。

### 2.3 与理论最优差距（DDS 上界达成率）——补绝对强度

`src/ai/bridge/dds.ts` 已有双明手求解器。对每个固定种子局：

- 用 DDS 求该局**双明手最优庄家得分**（绝对天花板）；
- 引擎在该局的实际得分 ÷ DDS 最优 = **该局达成率**；
- 跨局取平均 = 引擎的**绝对强度**（不依赖对手强弱，解决"对打结果受对手影响"的缺陷）。

这是把"AI 到底离完美还有多远"量化出来的关键指标，也是 RL 训练的天然监督信号。

### 2.4 分阶段独立评估

- **出牌（最难、权重最高）**：固定叫分/定主/扣底（沿用 A1/A2 的 `forcedBid`+固定 smart 思路），**只换出牌引擎**，比各引擎的出牌期望得分与残局正确率；
- **叫分**：固定其他阶段，比"该叫多少"与 DDS 最优叫分的差距（可参考 `B_bid_curve` 的难度曲线做校准）；
- **定主/扣底**：同样只换对应阶段引擎做消融。

### 2.5 人类基线

让作者/本地玩家打 N 局（可用决策日志导出），记录胜率、平均吃分，与引擎对比——作为"够不够强、够不够自然"的现实标尺（出牌自然度与可解释性也要主观评估，尤其 LLM）。

## 三、各引擎提升方向（基于已发现问题 + 架构）

> 原则：**先修 T0.4（跟牌退化），否则评估出来的 Bridge 强度是假的**。所有提升都必须过统一评估门槛才允许替换默认引擎。

- **BridgeEngine（当前默认）**
  - 最高优先：修跟牌退化（T0.4a 止血 / T0.4b 让跟牌也走 DDS）——跟牌约占一半决策，不修则强度被系统性低估；
  - 提升：采样从均匀改为**约束采样**（复用 `optimized/belief.ts`）、残局精准求解阈值下调、搜索预算自适应、领出策略/拔主时机强化。
- **AlgorithmEngine（约束采样）**
  - 提升：DP 均匀采样增加**对抗性**（采样对手最优而非均匀）、配对胜率搜索预算分配、信念残局求解增强；它和 Bridge 是"纯算法双雄"，对打结果值得最先跑。
- **LayaEngine（非自回归小模型）**
  - 提升：用 DDS/算法引擎的**高质量决策做监督蒸馏数据**、改进 top-k/温度采样、few-shot 注入；本质是"用强引擎教小模型"，成本低、见效快。
- **LlmEngine（大模型）**
  - 提升：prompt + few-shot 示例库、`reasoning_effort` 档位调优、结构化输出**校验+重试**、把 100 分明牌信息显式注入；进阶用 DDS 结果做 SFT/DPO 微调。注意 P99 延迟和回退率是它的首要工程指标。
- **通用**：引擎融合/多数投票成本高，最后考虑；先单引擎各自达标。

## 四、落地任务（追加到行动计划）

| ID | 任务 | 依赖 | 难度 | 验收 |
|---|---|---|---|---|
| **E1** | 修 T0.4 跟牌退化 | 无 | 中 | 评估噪音消除（跟牌不再空转） |

| **E4** | 分阶段评估（出牌/叫分/定主/扣底分开） | E2 | 中 | 每阶段一张质量表，定位短板 |

## 五、与 RL 的关系

统一评测是自训 RL（T3.2）的**验收装置**：先建这套 Elo/达成率评测并给 Bridge/Algorithm 立基线，再训 RL；RL 的训练奖励与评估也可直接复用 DDS 上界。**不要跳过评测直接训模型**——没有绝对标尺，RL 提升无法证明。

# 7. 补充建议

> 这一章是前面四阶段 + AI 评估之外、按"对项目走向的增量价值"补齐的建议。分「高价值 / 中价值 / 短期工程」，并给任务编号（G1–G8）便于逐项落实。

## G1（高价值）零对局数据是最大隐性短板

- **现状**：`decisionLogger` 只在内存记最近 200 条，项目**没有一行对局数据采集**。
- **为什么重要**：规划的 RL 自训、Laya 蒸馏、LLM 微调**全部依赖对局数据**，而现在没有任何语料积累。等真训时再收集就晚了。
- **建议**：尽早加**本地决策日志批量导出 + 匿名对局统计**——记录发牌、四阶段决策、结果、引擎类型，先攒几百上千局。
- **难度**：低（1–2h）。**验收**：可一键导出 N 局完整决策轨迹；字段覆盖引擎类型与四阶段动作。

## G2（高价值）用"预计算"消灭 AI 等待感

- **现状**：LLM 最长 8s 干等是体验硬伤；T1.6 只缓解（预计时长+取消）。
- **更彻底做法**：**轮到玩家之前预计算 AI 对手决策**——对手决策只依赖合法观察，可在玩家思考/出牌间隙预热并缓存。比加动画有效得多。
- **难度**：中（2–3h，需在 useGame/thinkingService 层做触发时机与缓存）。**验收**：玩家出牌后对手决策延迟大幅下降，多数轮次接近即时。

## G3（中价值）局外留存机制为零

- **现状**：单机无积分、段位、成就、连胜、历史战绩。
- **为什么重要**：棋牌是"低单局趣味、高复玩"品类，**留存几乎全靠局外系统**。
- **建议**：加本地战绩页（胜率 / 段位 / 成就 / 历史对局），比任何单局打磨都更能让玩家想回来打。
- **难度**：中（2–4h，可在 session/workbench 层落战绩）。**验收**：打完一局能看战绩与成就，可清零重开。

## G4（中价值）UI/组件测试基本空白

- **现状**：276 项测试全在引擎/AI 层，**UI 交互层零覆盖**；而已发现的 T0 bug 和出牌交互恰恰在 UI/编排层。
- **建议**：给最关键的交互补组件测试——叫分、点牌即出、扣底、重开确认，防止 T1.1/T1.7 类改动回归。
- **难度**：中（需引入组件测试框架，2–3h）。**验收**：上述 4 条关键交互各有防回归用例。

## G5（短期工程）文档已过时

- `README` 和 `docs/decision-engines-and-rl.md` 仍写"147 项测试"，实际已 276 项；功能清单、截图也落后。
- **建议**：顺手更新测试数、功能清单、玩法截图。开源门面的第一印象失真很扣分。
- **难度**：低（0.5h）。

## G6（短期工程）开源冷启动包装

- 技术质量极高却仅 1 star，差的是"让别人一眼看懂它牛在哪"的叙事。
- **建议**：30 秒玩法动图、一张四引擎对比图、一篇"为什么把测试做到 276 项"的技术博客；地方棋牌有天然地域话题（保山/腾冲本地玩家），是冷启动切入点。
- **难度**：低（内容产出，非代码）。**验收**：README 首页 10 秒可看懂价值。

## G7（短期工程）LLM 引擎的成本与合规

- 外接 qwen 等大模型有 **API 成本、密钥管理、隐私**三件事。
- **策略建议**：**本地 Laya 优先、LLM 只作对照**，避免产品被 API 成本绑架（架构已支持，只需把默认指向调优）。

## G8（方向性问题）明确项目定位

- 现状更像"**技术 showcase**"（四引擎、调试工作台、跨端、大量文档），而非"**有人玩的游戏**"。
- 两条路后续投入完全不同：技术 showcase → 继续打磨引擎与算法叙事；玩家游戏 → 开始做玩法留存与社区。
- **建议**：开工 Phase 1 前先定定位，它会决定 G3/G6 等项值不值得做。
