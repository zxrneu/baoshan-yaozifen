#### ✅ T0.2 提前结算阈值复核（2026-10-12 完成 · 结论：保留 `105−B`）

| 项 | 内容 |
|---|---|
| **位置** | `src/engine/game.ts:266`、`src/ai/bridge/dds.ts`（3 处）、`src/ai/bridge/heuristics.ts:100`、`src/ai/engines/llm/llmPrompts.ts:439`、`src/ai/optimized/simulator.ts:65`、`src/ai/optimized/policy.ts:70`、`README.md:33`、`TODO.md:4,16`、`docs/decision-engines-and-rl.md:58` |
| **原建议** | 把 `105−B` 改为 `101−B`，理由"数学上闲家必胜阈值为 `101−B`，当前保守 4 分" |
| **复核根因** | 原推理只做整数化（`100−D < B ⟺ D ≥ 101−B`），**漏掉分值粒度**。分牌仅 A/10=10、5=5（`src/cards.ts` `POINT_RANKS`），故任意累计吃分 `D` 恒为 **5 的倍数**；`D` 与 `100−B` 同为 5 的倍数时 `D > 100−B` 恒等价于 `D ≥ 105−B` |
| **结论** | `105−B` **已是精确锁定阈值**，非保守值；`101−B` 落在两个可达分值之间（B=70 时 31，而 D 只能取 30 或 35），**永不可达**。按原文改代码是**零行为变更** |
| **实测佐证** | 将 `src/ai/bridge/dds.ts` 三处 `105 - bid` 临时改为 `101 - bid`，对 60 随机发牌 × 3 叫分档 × 3 组初始分态（540 次全深度求解）生成 `moveScores` 指纹，与原始版本 **`diff` 无输出（逐字节一致）** |
| **实际改动** | **不修改任何阈值数值**；6 个源码文件补注"精确锁定阈值、勿改小"；`README.md` / `TODO.md` / `docs/decision-engines-and-rl.md` 修正公式说明（补明"底牌分只归庄家方"前提）；新增 `tests/early-finish-threshold.test.ts`（16 用例） |
| **回归测试** | `tests/early-finish-threshold.test.ts`：分值粒度不变量、`105−B` 与 `101−B` 全可达分判定一致性、参数化边界（B∈{70…100}）、判别性守卫（`100−B` 会误判）、DDS 剪枝不变性 |
| **验收** | 新增套件 16/16 通过；反向验证通过（改为 `100−B` 时 **7 个用例失败**，证明测试守得住；改为路线图主张的 `101−B` 时 **全部通过**，证明该改动确为零行为变更）；`npx tsc --noEmit` 退出码 0 |
| **⚠️ 严重度修正** | 原建议称"阈值偏保守 4 分 → 闲家已锁定仍空打、DDS 剪枝效率略损、README 公式声明错误"。实测：**不存在空打与剪枝效率损失**（阈值本就精确）；真正成立的只有"文档表述未写明其为精确值"，属**文档缺陷**而非代码缺陷 |

- **位置**：`src/ai/smart.ts` `buryFromObservation`、`src/ai/heuristic.ts` `aiBury`

- **方案**：兜底也仅在**非分牌**中选；若真无解（理论上极罕见），显式降级为"不扣够数并告警"或抛清晰错误，绝不返回含分牌的非法动作。

> **错在哪**：原推理只做了 `100 − D < B ⟺ D ≥ 101 − B` 的整数化，忽略了**分值粒度**——分牌只有 A/10=10、5=5（`src/cards.ts` `POINT_RANKS`），任意累计吃分 `D` 恒为 **5 的倍数**。当 `D` 与 `100−B` 同为 5 的倍数时，`D > 100−B` 恒等价于 `D ≥ 100−B+5 = 105−B`。`101−B` 落在两个可达分值之间，**永不被触达**（B=70 时 101−B=31，而 D 只能取 30 或 35）。
> **实测佐证**：在 `src/ai/bridge/dds.ts` 上把 3 处 `105 - bid` 临时改为 `101 - bid`，对 60 个随机发牌 × 3 个叫分档 × 3 组初始分态（共 540 次全深度求解）生成 `moveScores` 指纹，与原始版本**逐字节一致**（`diff` 无输出）。
> **实际改动**：保留 `105−B` 数值不变，在 6 个源码文件补注"精确锁定阈值、勿改小"；同步 `README.md`、`TODO.md`、`docs/decision-engines-and-rl.md` 的公式说明；新增 `tests/early-finish-threshold.test.ts`（16 用例）守护。

- **位置**：`src/engine/game.ts:266`、`src/ai/bridge/dds.ts`、`src/ai/bridge/heuristics.ts`、`src/ai/engines/llm/llmPrompts.ts`、`src/ai/optimized/simulator.ts`、`src/ai/optimized/policy.ts`、`README.md`、`TODO.md`、`docs/decision-engines-and-rl.md`
- **问题（原表述）**：当前用"闲家达到 `105−B` 立即结束/截断"，原以为数学上闲家必胜阈值为 `101−B`。
- **复核后的事实**：`105−B` **就是**精确阈值（受 5 分粒度约束），并非保守 4 分。原有代码与结算结果均**正确无误**，不存在"闲家已锁定仍空打"的浪费。
- **真正的问题**：仅在于**文档表述**把该值说成近似/保守，易诱导后人误改为不可达的 `101−B`；以及 `docs/decision-engines-and-rl.md` 的推导未写明"底牌分只归庄家方"这一前提。

# 5. AI 引擎效果提升与评估方案

> 聚焦：项目里四类决策引擎（**Bridge** 桥牌启发式+蒙特卡洛 / **Algorithm** 约束采样搜索 / **Laya** 非自回归小模型 / **LLM** 大模型）到底谁强、强多少、怎么提升、怎么证明提升有效。
> 核心结论：**评估先于提升**。你的 `experiments/` 已经是很好的消融设施，但目前只测"启发式/算法策略函数"，没把四类真实 `DecisionEngine` 放进同一套对打里，也没有绝对强度标尺。本文给一套完整框架。

## 一、你已有的评估设施（基础很扎实，别重复造）

`experiments/harness.ts` + `run.test.ts` 已经具备：

- 四阶段（叫分/定主/扣底/出牌）全部可注入策略的 `playHand` 对局驱动；
- `pairedDiff`（同种子跨策略**配对差分 95% CI**，消除发牌噪声）、`rateCI`、`bucketSuccess`（按牌力/分牌分层成局率）；
- `withDealer` **换位**（消除座位/叫牌顺序偏差）、`forcedBid(x)` 强制叫分、`roleSplit` **进攻/防守分开测**；
- 已有 A/B/C/D/E/F 六组实验：出牌消融（N=4000）、叫分难度曲线、定主消融、扣底消融、角色拆分、叫分策略对打；
- `decisionLogger` 记录运行中每次决策（供回放分析）。

**关键缺口**（也是这份方案要补的）：

| # | 缺口 | 后果 |
|---|---|---|
| 1 | 四类真实引擎未纳入统一对打 | `experiments` 测的是 `fastPlay/searchPlay/tacticPlay` 等**策略函数**，不是 `DecisionEngine`（bridge/algorithm/laya/llm），跨引擎强弱无结论 |
| 2 | 无跨引擎 Elo / round-robin | 无法回答"哪个引擎强、强多少、值不值得换默认" |
| 3 | 无"与理论最优差距"的绝对强度 | 现有是**相对消融**（A 比 B 好 0.5 分），依赖对手，无法度量"距最优还差多少" |
| 4 | 无分阶段独立质量指标 | 出牌被"成局率/庄分"间接度量，叫分/定主/扣底各自质量没分开量化 |
| 5 | 无模型级指标（LLM/Laya） | 延迟分布 P50/P99、非法率、重试率、超时回退率未入统一评测 |

## 二、统一评估框架（怎么评估）

### 2.1 指标分层定义

| 层 | 指标 | 含义 |
|---|---|---|
| 结果层 | 成局率、净得分、庄/闲方胜率、**Elo** | 综合强弱；Elo 用于跨引擎排序 |
| 决策层 | **出牌期望得分（副分）**、叫分准确率、定主质量、扣底质量、残局正确率 | 分阶段定位短板 |
| 运行层 | 合法率、延迟 P50/P99、超时率、回退率、重试率、决策一致性 | 工程可用性；LLM/Laya 尤其要看 P99 |
| 公平层 | 信息隔离校验通过率 | 明牌/暗牌不泄漏（沿用 `engine-fairness-isolation.test.ts`） |

### 2.2 对打协议（复用 harness，工作量最小）

1. **桥接**：为四类 `DecisionEngine` 各写一个 `DecisionEnginePolicy` 适配器，把 `chooseBid/chooseTrump/chooseBury/chooseCard` 包成 harness 的 `Policy`——这样**零改动**复用 `playHand`/`pairedDiff`/`withDealer`。
2. **Round-robin**：Bridge / Algorithm / Laya / LLM 两两对打 + 自对打，固定种子、东西/南北**换位各跑一遍**，N≥1000。
3. **基线锚点**：下限 = `random` / `min` / 出厂 `fast`；上限 = DDS 完美信息解（见 2.3）。
4. **产出**：每对组合的成局率、净得分 + 95% CI + **Elo 排行榜**（存 `experiments/results/`，延续现有 JSON 风格）。

### 2.3 与理论最优差距（DDS 上界达成率）——补绝对强度

`src/ai/bridge/dds.ts` 已有双明手求解器。对每个固定种子局：

- 用 DDS 求该局**双明手最优庄家得分**（绝对天花板）；
- 引擎在该局的实际得分 ÷ DDS 最优 = **该局达成率**；
- 跨局取平均 = 引擎的**绝对强度**（不依赖对手强弱，解决"对打结果受对手影响"的缺陷）。

这是把"AI 到底离完美还有多远"量化出来的关键指标，也是 RL 训练的天然监督信号。

### 2.4 分阶段独立评估

- **出牌（最难、权重最高）**：固定叫分/定主/扣底（沿用 A1/A2 的 `forcedBid`+固定 smart 思路），**只换出牌引擎**，比各引擎的出牌期望得分与残局正确率；
- **叫分**：固定其他阶段，比"该叫多少"与 DDS 最优叫分的差距（可参考 `B_bid_curve` 的难度曲线做校准）；
- **定主/扣底**：同样只换对应阶段引擎做消融。

### 2.5 人类基线

让作者/本地玩家打 N 局（可用决策日志导出），记录胜率、平均吃分，与引擎对比——作为"够不够强、够不够自然"的现实标尺（出牌自然度与可解释性也要主观评估，尤其 LLM）。

## 三、各引擎提升方向（基于已发现问题 + 架构）

> 原则：**先关闭 Phase 0 质量底线**（T0.1–T0.4 ✅ 均已完成），否则评估出来的 Bridge 强度可能是假的。所有提升都必须过统一评估门槛才允许替换默认引擎。

- **BridgeEngine（当前默认）**
  - ~~最高优先：修跟牌退化~~ ✅ 已完成——复核确认跟牌本就真实求解（无系统性空转），实际修的是静默吞异常与取消语义两类契约缺陷；
  - 提升：采样从均匀改为**约束采样**（复用 `optimized/belief.ts`）、残局精准求解阈值下调、搜索预算自适应、领出策略/拔主时机强化。
- **AlgorithmEngine（约束采样）**
  - 提升：DP 均匀采样增加**对抗性**（采样对手最优而非均匀）、配对胜率搜索预算分配、信念残局求解增强；它和 Bridge 是"纯算法双雄"，对打结果值得最先跑。
- **LayaEngine（非自回归小模型）**
  - 提升：用 DDS/算法引擎的**高质量决策做监督蒸馏数据**、改进 top-k/温度采样、few-shot 注入；本质是"用强引擎教小模型"，成本低、见效快。
- **LlmEngine（大模型）**
  - 提升：prompt + few-shot 示例库、`reasoning_effort` 档位调优、结构化输出**校验+重试**、把 100 分明牌信息显式注入；进阶用 DDS 结果做 SFT/DPO 微调。注意 P99 延迟和回退率是它的首要工程指标。
- **通用**：引擎融合/多数投票成本高，最后考虑；先单引擎各自达标。

# 7. 补充建议

> 这一章是前面四阶段 + AI 评估之外、按"对项目走向的增量价值"补齐的建议。分「高价值 / 中价值 / 短期工程」，并给任务编号（G1–G8）便于逐项落实。

## G1（高价值）零对局数据是最大隐性短板

- **现状**：`decisionLogger` 只在内存记最近 200 条，项目**没有一行对局数据采集**。
- **为什么重要**：规划的 RL 自训、Laya 蒸馏、LLM 微调**全部依赖对局数据**，而现在没有任何语料积累。等真训时再收集就晚了。
- **建议**：尽早加**本地决策日志批量导出 + 匿名对局统计**——记录发牌、四阶段决策、结果、引擎类型，先攒几百上千局。
- **难度**：低（1–2h）。**验收**：可一键导出 N 局完整决策轨迹；字段覆盖引擎类型与四阶段动作。

## G2（高价值）用"预计算"消灭 AI 等待感

- **现状**：LLM 最长 8s 干等是体验硬伤；T1.6 只缓解（预计时长+取消）。
- **更彻底做法**：**轮到玩家之前预计算 AI 对手决策**——对手决策只依赖合法观察，可在玩家思考/出牌间隙预热并缓存。比加动画有效得多。
- **难度**：中（2–3h，需在 useGame/thinkingService 层做触发时机与缓存）。**验收**：玩家出牌后对手决策延迟大幅下降，多数轮次接近即时。

## G3（中价值）局外留存机制为零

- **现状**：单机无积分、段位、成就、连胜、历史战绩。
- **为什么重要**：棋牌是"低单局趣味、高复玩"品类，**留存几乎全靠局外系统**。
- **建议**：加本地战绩页（胜率 / 段位 / 成就 / 历史对局），比任何单局打磨都更能让玩家想回来打。
- **难度**：中（2–4h，可在 session/workbench 层落战绩）。**验收**：打完一局能看战绩与成就，可清零重开。

## G4（中价值）UI/组件测试基本空白

- **现状**：276 项测试全在引擎/AI 层，**UI 交互层零覆盖**；而已发现的 T0 bug 和出牌交互恰恰在 UI/编排层。
- **建议**：给最关键的交互补组件测试——叫分、点牌即出、扣底、重开确认，防止 T1.1/T1.7 类改动回归。
- **难度**：中（需引入组件测试框架，2–3h）。**验收**：上述 4 条关键交互各有防回归用例。

## G5（短期工程）文档已过时

- `README` 和 `docs/decision-engines-and-rl.md` 仍写"147 项测试"，实际已 276 项；功能清单、截图也落后。
- **建议**：顺手更新测试数、功能清单、玩法截图。开源门面的第一印象失真很扣分。
- **难度**：低（0.5h）。

## G6（短期工程）开源冷启动包装

- 技术质量极高却仅 1 star，差的是"让别人一眼看懂它牛在哪"的叙事。
- **建议**：30 秒玩法动图、一张四引擎对比图、一篇"为什么把测试做到 276 项"的技术博客；地方棋牌有天然地域话题（保山/腾冲本地玩家），是冷启动切入点。
- **难度**：低（内容产出，非代码）。**验收**：README 首页 10 秒可看懂价值。

## G7（短期工程）LLM 引擎的成本与合规

- 外接 qwen 等大模型有 **API 成本、密钥管理、隐私**三件事。
- **策略建议**：**本地 Laya 优先、LLM 只作对照**，避免产品被 API 成本绑架（架构已支持，只需把默认指向调优）。

## G8（方向性问题）明确项目定位

- 现状更像"**技术 showcase**"（四引擎、调试工作台、跨端、大量文档），而非"**有人玩的游戏**"。
- 两条路后续投入完全不同：技术 showcase → 继续打磨引擎与算法叙事；玩家游戏 → 开始做玩法留存与社区。
- **建议**：开工 Phase 1 前先定定位，它会决定 G3/G6 等项值不值得做。
