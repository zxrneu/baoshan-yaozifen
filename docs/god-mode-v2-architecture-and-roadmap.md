## 1. 定位、目标与非目标

上帝模式用于开发调试和算法调优：开发者可以观察完整牌局，接管当前行动，保存并复现问题，在相同条件下比较不同策略。工作台的价值首先是执行正确、信息边界清楚、结果可以追溯。

### 1.1 核心目标

| 目标 | 必须形成的闭环 |
|---|---|
| **全阶段、全座位合法接管** | 叫分、定主、扣底、出牌均可替当前行动座位操作；支持暂停、单步、自动运行、撤销与重做 |
| **可靠的异步执行** | 换引擎、改参数、撤销、重开、导入和手动接管后，旧请求不能修改新局面或覆盖当前诊断 |
| **坏局复现** | 完整、版本化 JSON 快照可导出、校验、导入并继续运行；另行支持保存动作后的确定性回放 |
| **全阶段决策追溯** | 区分“请求过哪些建议”和“实际执行了什么”；记录局面、配置、耗时、异常、降级和动作来源 |
| **座位独立策略配置** | 四个座位均可配置 Human 或现有 AI，引擎、模型、Prompt 与搜索参数按配置实例隔离 |
| **可信的算法比较** | 同一节点比较多个引擎；通过共享运行内核进行无界面对战，输出配对结果与统计不确定性 |
| **可用的工作台界面** | 在常用桌面和笔记本视口中看清手牌、当前行动与诊断；键盘操作与按钮行为一致 |

核心能力只要求现有可用引擎：Bridge、Algorithm、LLM、Laya。某引擎不支持某阶段或某诊断指标时，应明确显示能力限制或记录降级，不承诺所有引擎具有相同能力。

### 1.2 后续增强目标

以下能力保留在设计范围内，按第 8 节的先后顺序实施，不作为首个可用版本的前置条件：

- **可视化残局编辑器**：从完整快照修改局面，或显式构造缺少历史的实验场景。
- **历史分支树界面**：在已经可靠的撤销、重做和节点关联上增加分支浏览与结果比较。
- **Perfect Information Oracle**：用真实完整牌分布评估指定节点，明确精确性与优化目标。
- **YZF-FEN**：在 JSON 协议稳定后定义紧凑局面格式及其信息损失边界。
- **高级诊断**：DDS 搜索统计、Prompt Playground、模型返回的策略概率及熵可视化。

### 1.3 非目标

| 非目标 | 范围说明 |
|---|---|
| 在正常对局执行路径中跳过轮次或跟门规则 | 接管通过原规则引擎执行；非法输入用于验证拒绝行为。状态编辑和故障注入另设入口 |
| 工作台透视自动赋予 AI 全知能力 | UI 看牌权限与 AI 观察权限独立；普通策略始终使用规定的可见信息 |
| 全面重写游戏规则与所有决策算法 | 工作台复用现有规则与引擎；影响结果可信性的缺陷作为明确的依赖修复 |
| 任意完整牌局都能快速得到精确 Oracle 值 | 搜索可能受节点、时间或深度限制；近似结果必须标明，不能作为精确真值 |
| 保证所有远端模型在统一固定时限内完成 | 每项结果独立展示，有超时、取消、失败与降级状态；移除“全引擎两秒完成”的验收要求 |
| 仅靠相同发牌 seed 保证重新推理得到相同动作 | 搜索随机源、预算与模型输出另行记录；确定回放执行保存的动作 |
| 将模型自报置信度、选牌概率视为校准胜率 | 保留各指标的含义与来源；统一评价需使用独立的公共评估协议 |
| 推测未返回的模型内部信息 | 只展示引擎实际提供的诊断与解释，不承诺完整思维链、注意力权重或原始 logits |
| 完整 RL 训练平台、自动训练或线上天梯 | 本次提供可复用实验入口；训练管线、分布式调度与排名服务另立设计 |
| 首版支持所有地方规则变体与跨版本无限兼容 | 快照首版支持 `basic-v1`；未知版本或规则显式拒绝，迁移按版本逐项实现 |

### 1.4 首版实际交付边界

首版实现步骤 1～3，并把已有 LLM 全阶段接口接入共享会话。核心代码为 [GameSession](../src/workbench/session.ts)、[快照编解码与校验](../src/workbench/snapshot.ts)、[useGame](../src/hooks/useGame.ts) 和 [联合验证入口](../scripts/evaluate-god-llm.ts)。验证结果记录在 [首版联调评估](god-mode-v1-validation.md)。

- 正常对局仍由南家人工操作；工作台的「AI 代走一步」明确授权当前座位由 AI 行动，「四座 AI 连打」将本副四座全部交给当前统一引擎，副结束后等待下一副操作。
- 手动接管任何阶段、撤销、恢复、重开或导入后暂停。没有手动选牌时，AI 代走请求当前引擎，不再使用第一张牌、最低叫分等隐式默认动作。
- 首版只允许一个活动评估，Next / Hint / 预计算复用同一请求；会话游标控制提交。模型与远端引擎在换配置时创建新实例，旧请求被取消。
- 日志覆盖四个阶段；评估记录标明“仅评估 / 已执行 / 已失效”，提交记录关联 requestId，人工动作单独记录来源。唯一候选快路径和算法回退不计为模型成功。
- 快照保存全部规则状态和有界线性动作路径，支持重放已执行动作；模型连接参数使用本机设置，导入后明确暂停。逐座位 profile、配置包导入、分支树和配对策略评测留给步骤 4～7。
- LLM 请求同步模型、协议、超时、响应格式和推理设置；服务端地址与鉴权由服务端运行环境提供，响应和日志保留实际模型、原始输出及回退原因。
- 首版验证脚本评估执行正确性、模型响应和回退率，不把单副胜负或已有启发式评分当成棋力结论。

## 2. 现状与需要修复的基础问题

以下诊断基于评审时的实现。后续实施前应确认相关文件的最新变化。

| 现状 | 对调试的影响 | 设计处理 |
|---|---|---|
| `godModeEnabled`、`devPeekSeats`、`isDebugMode`、全明手派生状态承担不同含义 | UI 透视、布局和控制权限容易混淆 | 分离视图偏好、执行状态、座位控制与信息权限 |
| 非出牌阶段按钮和处理函数绑定人类南家 | 电脑叫分、定主、扣底无法直接接管 | 所有操作显式指定行动座位，通过统一命令入口提交 |
| 单步预计算、Next、Hint 使用不同的异步路径 | 旧建议可能落到新局面；重复推进可能产生重复请求 | 建立统一请求上下文、取消与提交校验 |
| 自动连打未统一进入 `historyStack`；重开未统一重置历史及请求 | 撤销不完整，可能跨会话回到旧局面 | 所有成功动作经过同一提交路径 |
| 预推演或提示已写决策日志，但实际动作未必采用 | 日志条数和执行步数混在一起 | 分别记录评估与动作提交，按节点关联 |
| `thinkingService` 只有一个当前状态；面板主要读取最新日志 | 多引擎、同座位并行请求会互相覆盖或展示旧结果 | 按会话、节点、请求和配置实例隔离 |
| “完整 GameState 快照”按钮实际只导出部分字段 | 无法完整恢复规则、轮次、叫分和比分等上下文 | 引入专用快照编码器、解码器和校验器 |
| `RuleConfig.scoring` 是函数 | 直接 JSON 序列化后丢失，规则识别与结算会出错 | 保存 `ruleId` 和纯数据参数，从规则注册表恢复函数 |
| 全局引擎管理器共享可变引擎；南家在自动驱动中被硬编码跳过 | 难以支持同类引擎不同参数及四 AI 对战 | 配置实例路由与显式 Human/AI 座位控制 |
| 已有 DDS，但未提供任意节点的可靠 Oracle 入口 | 缺少当前墩支持；截断状态和得分语义尚需验证 | 作为后续 Oracle 的依赖修复，而非从零另建求解器 |

主要入口：

- 对局编排：[useGame.ts](../src/hooks/useGame.ts)
- 规则状态与转换：[engine/types.ts](../src/engine/types.ts)、[engine/game.ts](../src/engine/game.ts)、[engine/rules.ts](../src/engine/rules.ts)
- 工作台 UI：[SquareTable.tsx](../src/components/SquareTable.tsx)、[DebugSidePanel.tsx](../src/components/DebugSidePanel.tsx)、[ControlPanel.tsx](../src/components/ControlPanel.tsx)
- 决策适配与协议：[engineAdapter.ts](../src/ai/engines/engineAdapter.ts)、[decisionProtocol.ts](../src/ai/engines/decisionProtocol.ts)
- 现有实验与评测原则：[harness.ts](../experiments/harness.ts)、[算法评测设计](./optimized-ai-algorithm.md#122-胜率和耗时)

## 3. 架构边界与数据流

### 3.1 统一运行内核

工作台 UI 与无界面实验共用同一套命令、规则转换、观察投影和动作校验。React Hook 负责订阅与展示，不再独立维护多条执行链。

~~~mermaid
flowchart TD
    UI["工作台 UI / useGame"]
    BATCH["无界面实验 Runner"]
    SESSION["DebugSession / 统一命令与提交"]
    HISTORY["历史节点与动作事件"]
    CODEC["快照编解码与校验"]
    EVAL["EvaluationService / 请求调度"]
    PROJECT["阶段观察投影"]
    ROUTER["SeatAgentRouter / 配置实例路由"]
    ENGINE["现有本地或服务端引擎"]
    RULES["现有游戏规则引擎"]
    LOGS["评估记录与诊断"]
    ORACLE["OracleEvaluator / 后续独立能力"]

    UI --> SESSION
    BATCH --> SESSION
    CODEC --> SESSION
    SESSION --> RULES
    RULES --> HISTORY
    SESSION --> EVAL
    EVAL --> PROJECT
    PROJECT --> ROUTER
    ROUTER --> ENGINE
    ENGINE --> LOGS
    LOGS --> UI
    SESSION --> ORACLE
    ORACLE --> LOGS
~~~

规则引擎仍是合法动作的唯一执行依据。Oracle、提示和横向比较只产生评估结果，采纳建议时统一走命令提交路径。

### 3.2 模块职责

| 模块 | 职责 |
|---|---|
| `DebugSession` | 持有局面、游标、运行模式和配置版本；处理暂停、推进、接管、撤销、重做、换副与重置 |
| `EvaluationService` | 创建请求上下文，调度引擎、去重、取消、验证结果和管理建议缓存 |
| `SeatAgentRouter` | 将座位配置解析为不可变的引擎配置实例；处理阶段能力、执行环境和显式降级 |
| `ObservationProjector` | 按阶段构造允许 AI 使用的信息；UI 透视不参与普通观察投影 |
| `SnapshotCodec / Validator` | 编解码纯数据快照、版本迁移、规则恢复与完整性校验 |
| `HistoryStore / DecisionStore` | 保存节点、提交动作与评估记录；提供当前路径与跨分支查询 |
| `BenchmarkRunner` | 独立创建实验会话，执行配对对战、聚合指标并导出实验清单 |
| `OracleEvaluator` | 使用真实牌分布评估指定动作，声明目标、求解状态和界限；独立于普通策略观察 |

建议新增 `src/workbench/` 放置上述契约与运行内核。首步只抽取解决调度和状态一致性所需的最小模块，不要求一次完成所有目录迁移。

### 3.3 状态分别管理

- **游戏状态**：`GameState`，只经规则动作或校验通过的导入、编辑入口更新。
- **运行状态**：当前会话、节点、运行模式、请求状态；不随 UI 透视切换。
- **视图偏好**：工作台开关、透视座位、牌面朝向、面板宽度与选项卡。
- **策略配置**：Human/AI 座位绑定、引擎配置实例及版本。
- **评估与历史**：实际动作路径、候选建议、请求诊断与分支关系。

可持久化视图偏好和策略配置。活动请求、AbortController 和自动运行状态不持久化；刷新或重新进入工作台后从暂停状态恢复。

## 4. 调试会话、控制与历史

### 4.1 基础契约

以下类型用于说明职责边界；落地时复用现有领域类型，按模块拆分。

~~~typescript
type Seat = 0 | 1 | 2 | 3;
type ExecutionMode = 'paused' | 'step' | 'auto';
type DecisionPhase = 'bidding' | 'trump' | 'bury' | 'playing';
type JsonValue =
  | null | boolean | number | string
  | JsonValue[] | { [key: string]: JsonValue };

interface WorkbenchViewState {
  active: boolean;
  peekEnabled: boolean;
  peekedSeats: Seat[]; // 持久化使用数组，运行时可派生 Set
  cardOrientation: 'player' | 'viewer' | 'suitMatrix';
}

interface EngineProfile {
  id: string;
  engineType: EngineType;
  revision: number;
  transport: 'local' | 'server';
  parameters: Record<string, JsonValue>;
  fallbackProfileId?: string;
}

type SeatControl =
  | { kind: 'human' }
  | { kind: 'ai'; profileId: string };

type SeatControls = Record<Seat, SeatControl>;

interface SessionCursor {
  sessionId: string;
  nodeId: string;
  epoch: number;
  configRevision: number;
}

interface EvaluationContext extends SessionCursor {
  requestId: string;
  seat: Seat;
  phase: DecisionPhase;
  profileId: string;
  profileHash: string;
  purpose: 'prefetch' | 'step' | 'auto' | 'hint' | 'compare';
}
~~~

`parameters` 由各引擎的参数 schema 校验，不能作为任意对象直接透传。模型标识、Prompt 内容或版本与哈希、搜索预算、独立搜索随机源等属于配置；鉴权凭据通过运行环境解析，不放入可分享快照。

同一种引擎允许多个 profile，例如两种 Bridge 搜索预算、两个 LLM 模型或两个 Prompt 版本。请求启动时固定 profile 快照，计算过程中不读取可变的“当前全局引擎”。

### 4.2 运行模式与操作语义

| 操作 | 明确行为 |
|---|---|
| 进入工作台 / Pause | 停止自动提交并取消尚未提交的自动任务；进入暂停。可显式请求 Hint 或 Compare |
| Step 模式 | 当前 AI 座位可预计算建议；建议完成后等待 Next，不自动执行 |
| Next | 对当前游标最多提交一次合法动作；无可用建议时按当前配置请求一次决策 |
| Human 轮次的 Next | 正常对局只提交人工选择；工作台的明确 AI 代走入口可请求当前座位的 AI 决策，不使用隐式默认动作 |
| Auto | 首版工作台四座使用统一 AI，副结束后等待下一副；正常对局遇到南家等待输入。步骤 4 后按座位配置执行；不可恢复错误暂停并展示原因 |
| Manual Takeover | 在任意阶段替当前行动座位提交合法动作，取消竞争请求并暂停自动运行 |
| Hint | 只产生建议，不推进；只有显式采用或确认后才执行 |
| Undo / Redo / 切换历史节点 | 先暂停并使请求失效，再切换节点；保留当前引擎配置，以便试验另一策略 |
| 更换引擎、参数或 Prompt | 更新配置版本，使旧建议失效；按当前模式决定是否重新预计算 |
| Restart | 按保存的本副起点或导入场景根重开，创建新会话；保留起点的 dealer、规则与比分上下文 |
| 导入 / 保存场景编辑 | 校验成功后创建新会话根并暂停；失败时保留原会话 |
| Next Hand | 通过同一命令提交路径推进；副终结可进入下一副，matchEnd 显示新比赛入口 |

`paused`、`step`、`auto` 描述执行方式；是否正在评估属于每个请求的状态。首版只运行一个活动请求，`isThinking` 从会话任务派生；并行比较接入后按 requestId 分别展示。

### 4.3 异步结果的接纳与提交

1. 请求启动时捕获完整 `EvaluationContext`、不可变局面和配置快照。
2. 暂停自动执行、接管、撤销、重做、重开、导入、节点切换及配置变化，同步更新失效标记并取消关联请求；不能只等待 React effect 清理。
3. `epoch` 单调增加，Undo 回到旧节点也不能把 epoch 回滚，防止旧请求在同一节点重新“变有效”。
4. 进度回调、完成回调、建议缓存写入和动作提交均核验请求上下文。
5. 返回动作还要校验阶段、座位、动作种类与合法性。超时、非法动作、异常和降级分别记录。
6. Abort 是节省资源的手段；即使引擎忽略 Abort 或返回得更晚，游标检查也必须拒绝其修改当前状态。
7. Next 与自动提交经统一串行入口执行；同一游标重复触发不能提交两次。
8. 日志可保留过期或取消请求供排查，但这些记录不能成为当前节点的推荐动作或实时诊断。

建议缓存至少绑定会话、节点、epoch、配置版本、阶段、座位和 profile 哈希。同节点比较中允许多个请求同时存在，必须按请求身份隔离。

### 4.4 全阶段合法接管

“全座位”表示不受 Human/AI 身份限制，行动顺序仍由规则引擎确定。

| 阶段 | 开放操作 | 必须验证 |
|---|---|---|
| 叫分 | 为当前叫分者选择合法分数或不叫 | 当前叫分者、合法分档及既有叫分历史 |
| 定主 | 为当前庄家选择花色，并展示该庄家的花色统计 | 庄家身份、阶段、花色枚举 |
| 扣底 | 从当前庄家手牌多选、推荐或清空扣底牌 | 恰好 4 张、不重复、在手牌中且不含 A/10/5 分牌 |
| 出牌 | 为当前行动座位选牌、确认或采用 AI 建议 | 手牌归属、轮次、跟门规则 |
| 副间推进 | 下一副、新比赛或按保存起点重开 | 副终结与比赛终结分别处理 |

UI 的手牌、选中态、统计和处理函数都依据当前操作座位。正常玩家界面保持原控制权限。

修改合同、换领出者、重分配手牌属于场景编辑。若当前墩已出牌，不能仅改 `leader`；需要回到墩开始节点或明确重建整墩，并重新校验牌张与计分。非法动作测试向规则入口提交非法输入并验证拒绝；后续故障注入如需运行无效状态，应使用独立实验环境。

### 4.5 历史节点与动作记录

~~~typescript
type GameCommand = AiAction | { kind: 'nextHand' };

interface CommittedStep {
  command: GameCommand;
  source: 'human' | 'ai' | 'manual' | 'comparison';
  evaluationId?: string;
}

interface HistoryNode {
  id: string;
  parentId: string | null;
  childrenIds: string[];
  state: GameState;
  incomingStep: CommittedStep | null;
}
~~~

手动动作、自动动作、单步动作和换副全部经相同提交路径：验证游标与命令、执行规则转换，再原子更新当前节点、动作记录与 UI 派生状态。失败不创建历史节点。

先提供线性的撤销、重做界面，节点身份与来源字段从第一步保留。分支存储与树形界面后续实现；首版若采用线性历史，撤销后新动作将清空 redo 路径，界面应明确这一行为。

采用分支树后，撤销只移动游标；继续执行创建新的 child。评估日志按节点关联，查看当前路径时筛选其关联记录，不通过删除全局日志实现“回滚”。重开或导入建立新会话，旧会话记录按有界保留策略归档，不能混入当前历史。

## 5. 快照、回放与场景校验

### 5.1 三种可复现能力分别验收

| 能力 | 保证 |
|---|---|
| 状态恢复 | 导入后游戏状态、规则及各阶段可见观察与原状态一致，可继续合法运行 |
| 动作回放 | 从保存起点执行已保存命令序列，逐步还原局面，不重新请求模型 |
| 重新评估 | 在记录的配置与预算下再次求解；固定搜索随机源有助于复核，但远端模型与时间预算不保证相同输出 |

发牌 seed 不等于搜索随机 seed。实验使用独立搜索随机源，并记录种子或随机流标识、搜索预算与算法版本；普通 AI 输入不携带可用于反推暗牌的发牌 seed。

### 5.2 版本化 JSON 为首个权威协议

~~~typescript
type SerializableGameState =
  Omit<GameState, 'rules'> & {
    rules: Omit<RuleConfig, 'scoring'>;
  };

interface GameSnapshotV1 {
  format: 'game-snapshot';
  schemaVersion: 1;
  ruleSetId: 'basic-v1';
  exportedAt: string;
  state: SerializableGameState;
  config: { activeEngine: EngineType };
  replay?: {
    initialState: SerializableGameState;
    commands: Array<AiAction | { kind: 'nextHand' }>;
  };
}
~~~

- 保存 `GameState` 的全部纯数据字段，包括 dealer、bidOrder、bidding、highestBidder、leader、当前墩、完整墩历史、上一墩、双方计分、比赛比分、结果、seed 和规则参数。
- `ruleSetId` 通过规则注册表恢复函数，并校验参数与顶层状态的一致性。未知规则不能悄悄回退为默认规则。
- JSON 数据不包含函数、Set、活动请求或可执行脚本。读取成功不代表校验通过。
- 首版 `game-snapshot` 只接受完整历史。无历史残局在步骤 8 定义独立的 scenario 协议，明确已出牌区域和观察投影后再支持导入，不能复用这个结构并省略历史。
- 导入完成时生成新会话与根节点，清空选牌、底牌揭晓弹窗、待执行建议和实时思考状态。
- 不带 replay 时只恢复当前局面；带 replay 时先校验起点和全部命令，并确认最终状态与 state 一致，导入后可撤销/恢复保存的路径。不能撤销到导入前的会话。首版线性路径最多保留 1000 个节点，超过后以前置检查点作为回放起点。
- 如需分享整棵分支树与评估过程，后续使用单独的 session bundle，避免普通快照过大。
- 旧版局势诊断片段因缺少完整协议与历史而拒绝导入；后续只有能无歧义恢复的内容才可迁移，不能补默认值后宣称完整复现。
- 首版 config 只恢复当前引擎类型，模型、Prompt 与连接参数使用本机设置，UI 明示这一边界；因此保证状态与动作回放，不保证重新推理一致。步骤 4 增加配置包和逐座位 profile 时升级快照版本；凭据仍由运行环境解析。

### 5.3 按阶段验证状态

本规则使用 52 张无大小王牌，分牌为 A/10/5，总分 100。校验区分“牌张所有权”和“同一张牌的历史引用”。

| 阶段 | 牌张与牌数约束 |
|---|---|
| bidding / trump | 四家各 12 张，底牌 4 张，52 张牌的所有权唯一且完整 |
| bury | 庄家 16 张，其他各 12 张；当前 `kitty` 是原摸入底牌的引用，已包含在庄家手牌中，不能再计入独立牌区 |
| playing，完整历史 | 各家剩余牌数为 `12 - 已完成墩数 - 本墩是否已出牌`；手牌、扣底、已完成墩和当前墩共同分割 52 张牌 |
| handEnd / matchEnd | 支持提前结束后仍有剩余手牌；按实际完成墩、计分和终结规则验证，不能强制四家手牌为空 |

额外检查：

- 花色、点数、座位、阶段及所有数值范围合法，禁止重复牌和越界枚举。
- `lastTrick` 是上一墩的重复引用，不再计作独立牌区；其赢家和分数与历史一致。
- `bidOrder`、`bidding`、最高叫分、叫分者与当前阶段一致；每次叫分符合规则。
- 主牌、庄家、leader、当前墩出牌顺序与当前行动座位一致。
- 完整出牌历史的赢家、分数、跟门合法性与累积计分一致；缺门信息由历史推导。
- `trickNumber` 按阶段验证：出牌中的下一墩与提前结束时的终结墩不能套用同一个加一公式。
- 计分守恒检查实际牌区及历史，不把已吃分与同一批历史牌的点数重复相加。扣底后的底牌不得含分牌。
- 比赛比分、targetWins、结算结果与是否提前结束一致。
- 超大输入、未知版本、缺字段或不一致状态返回可定位的错误，校验过程不修改活动会话。

先完成纯函数校验与测试，再接入粘贴导入 UI。校验通过后才进行替换，不设置“十毫秒重构状态树”的硬性承诺。

### 5.4 可视化场景编辑

编辑器使用 52 张牌；先支持基于完整快照编辑，并复用 JSON 校验器。

- 牌张可以分配给四家手牌、底牌、当前墩和明确的已出牌区域；已有历史引用与所有权必须一致。
- 调整手牌、合同、主牌、比分或领出者后生成新的构造场景根，保留来源节点与编辑摘要。
- 比分应与历史或构造的已收牌分配一致，不能只编辑显示数字。
- 完整历史场景按第 5.3 节验证；未记录出牌顺序的构造残局标记 `historyCompleteness: 'unavailable'`，不能伪造完整历史。
- 无历史残局需要独立的场景表示与已出牌信息投影，不能只把 `completedTricks` 置空后交给现有采样器。
- 有限信息引擎必须声明支持这种输入；不支持时拒绝评估并说明原因。Oracle 可在牌分布和当前墩完整时独立评估。
- 构造场景用于定向实验，正式整局对战报告默认使用正常发牌样本；两类结果分开标注。

### 5.5 YZF-FEN 的边界

FEN 后于 JSON 和场景表示实施，独立补充格式规范后再编写解析器。

规范至少明确版本、座位顺序、阶段、规则标识、主牌、庄家、合同、leader、四家手牌、底牌、当前墩和计分，以及转义和可选扩展规则。示例必须由编码器生成并通过校验。

FEN 是紧凑局面表示。只有完整携带历史的扩展格式才能保证普通 AI 观察等价；基础格式若缺少历史，按构造残局处理。不能承诺通过剩余手牌反推唯一的叫分或出牌历史，也不能以 FEN 替代完整坏局快照。

## 6. 引擎路由、比较与诊断

### 6.1 座位与配置实例解耦

默认正常对局维持南家 Human、其余 AI；工作台四个座位均可独立配置 Human 或 AI。自动驱动依据 `SeatControl`，去掉南家自动跳过的硬编码。

profile 包含引擎类型、执行环境、模型、Prompt 版本或内容哈希、搜索参数、请求超时及降级配置。支持南北 A 对东西 B，也支持同类引擎的参数消融。全局预设用于一次更新多个座位，之后仍可逐座位调整。

本地和服务端请求使用相同的 profile 快照语义。不能只更新客户端下拉框，而让服务器继续使用旧模型或旧参数；响应记录实际生效的配置与执行环境。profile 的合法字段及可覆盖项由各引擎显式定义。

### 6.2 全阶段信息边界与能力声明

- 普通 AI 的叫分、定主、扣底、出牌都使用对应阶段的可见观察；出牌阶段复用 `PlayerObservation`。
- 叫分与定主只提供本家手牌及公开上下文；扣底可提供庄家摸底后的手牌。未知对手手牌及未知底牌不能因日志或工作台透视进入普通请求。
- 逐步以阶段观察契约替代直接把完整 `GameState` 传入普通 `chooseAction` 的接口。迁移期在适配器和服务端落实字段白名单。
- 引擎声明支持的阶段、指标、取消能力及是否支持无历史场景；未实现阶段采用明确的备用策略并记录原因。
- 降级配置不得成环；主引擎与备用策略共用该次请求的总预算，不能通过层层回退无限延长决策。
- Oracle 使用单独的完整状态评估接口；普通请求不带一个可隐式绕开观察投影的全知开关。

### 6.3 同节点多引擎比较

1. 比较固定当前节点、行动座位、阶段、观察与候选动作，暂停自动提交。
2. 出牌比较默认使用全部合法候选牌。引擎内部剪枝需记录筛掉的动作，不能把被剪掉的牌称为非法牌。
3. 每个配置实例拥有独立请求、结果、进度和取消状态；相同座位的多个引擎不共享一个实时思考槽位。
4. 按结果完成顺序展示卡片，分别标识等待、完成、超时、取消、失败、无能力或降级。
5. 每张卡片展示请求配置、实际引擎、推荐动作、解释、端到端耗时和引擎计算耗时（可获得时）。
6. 只有原节点和配置上下文仍有效时才能“采用此动作”；采纳后通过统一提交路径生成动作事件，其他建议变为旧节点记录。
7. 比较首先支持出牌；扩展到叫分、定主、扣底时使用对应的候选动作 schema，不强行复用 `chosenCard`。
8. 多个 Promise 不代表 CPU 搜索真正并行。CPU 引擎放入 Worker 或受限任务池，远端请求设置并发限制。

### 6.4 评估记录与执行记录分别保存

评估记录至少包含：

| 类别 | 字段或语义 |
|---|---|
| 身份 | evaluationId、完整请求上下文、节点、阶段、座位、用途 |
| 配置 | 请求 profile 快照与哈希、实际生效引擎/模型、执行环境 |
| 输入 | 观察或其摘要、候选动作、Prompt 模板版本；完整局面通过节点引用 |
| 输出 | 推荐动作、候选评估、结构化解释、引擎返回的原始响应 |
| 状态 | 完成、取消、过期、超时、非法结果、异常；降级原因与实际备用策略 |
| 成本 | 端到端耗时、可获得的计算耗时、搜索统计与模型调用信息 |

实际提交记录包含前后节点、命令、来源与可选 evaluationId。Human 和手动接管也写动作记录，但不伪装成 AI 推理。评估未被采用仍可查看，不计作执行步数。

`DecisionRecord` 改为按阶段的联合结构：叫分保存 bid/pass，定主保存花色，扣底保存多张牌，出牌保存单张牌。所有阶段均记录正常和降级结果。历史面板查询当前会话、节点与请求，不能只凭“同一座位”或“最后一条日志”关联推荐。

内存日志采用有界保留；批跑结果另行导出文件，不依赖当前最多若干条记录的全局单例。请求与响应审查在记录端过滤鉴权数据，导出保持同样的过滤规则。

### 6.5 指标的语义与可获得性

| 指标 | 含义与展示规则 |
|---|---|
| 搜索胜率 | 说明所属方、样本分布、后续策略与样本数；属于该评估协议下的估计 |
| 期望分 | 说明庄方/闲方视角、是否包含已有分数、是否采用提前结束规则 |
| 策略概率 | 在明确候选集合上的选牌概率，不是赢副率；概率未归一或候选不全时标注 |
| 模型置信度 | 模型自报值，单独展示，不参与统一胜率排序 |
| DDS 搜索统计 | nodes、ttHits、prunedBranches、最大已展开深度及终止原因；指标未暴露时显示不可用 |
| 概率熵与 Top 差值 | 熵为 `-Σ p log p`，Top-1/Top-2 差值为两项概率之差，分开标注 |
| logits / 模型解释 | 仅显示模型实际返回的内容；有概率不等于获得原始 logits 或内部注意力 |

统一比较算法收益时，使用相同的信息条件、公共评价目标与预算；不能直接排序不同引擎各自输出的 confidence、probability 和 winRate。

Prompt Playground 在 profile 草稿上修改，保存产生新版本并使旧请求失效；同节点重新评估不自动执行动作。模板与渲染后的请求可审查，但不把未返回的内部推理作为验收项。

### 6.6 Oracle 契约与进入条件

Oracle 是后续诊断工具，复用并修正现有 DDS。实施前必须补齐：

- 支持已有 0～3 张牌的当前墩、正确行动座位和各家不等长的剩余手牌。
- 明确目标：赢副值与终局吃分值分别求解；赢副目标中的 100/0 截断标记不能展示为真实吃分。
- 明确遵循的规则及终止条件，特别是基础规则的提前结束。
- 返回精确、上下界、深度限制、节点限制、超时或取消状态；触及限制不能继续标记 `exact`。
- 候选动作分别声明数值精确性；Alpha-Beta 窗口导致的界限不能作为所有候选的精确分数。
- 通过小规模独立穷举验证中途跟牌、双方视角、节点截断和目标截断。
- 对所有有限信息策略保持独立观察投影，Oracle 的完整牌分布不回流到策略请求。

regret 采用当前行动方的共同收益定义：`V*(s) - V(s, a)`。只有最优值与动作值在相同目标下被精确验证时，才能报告精确 regret；有界结果报告区间，近似结果报告估计。按真实牌分布得到的全知值是该局面的完全信息参照，不等同于有限信息博弈的最优策略值。

## 7. 无界面评测与工作台交互

### 7.1 共享内核的实验 Runner

复用现有 `experiments/harness.ts` 的配对思路，通过不依赖 DOM、音效、localStorage 或全局 UI 服务的运行内核执行异步引擎对战。

每个实验拥有独立会话、profile、随机源和记录空间；设置并发上限、每决策预算、每副最大动作数、重发牌上限和停止条件。用户取消批跑后不能继续写入当前工作台局面。

实验清单保存 app/算法版本、规则、样本集合、阵营与座位轮换、模型与 Prompt 版本、预算、独立随机源、信息条件和降级策略。100 副等小批跑用于调试实验流程，样本数是否足够由置信区间和目标提升幅度决定。

### 7.2 公平比较协议

- 同一发牌样本交换双方并轮换座位，按一个发牌样本组计算配对差和不确定性。
- 出牌算法消融固定叫分、定主、扣底；全生命周期策略对战另行评测，避免把合同难度变化误认为出牌提升。
- 正式策略对战使用相同普通信息权限；Oracle 或其他全知实验单独标注，不能混入公平策略胜率。
- 训练、调参与最终评估样本分开；用于调试的固定坏局集单独报告。
- 固定时间预算与固定节点/样本预算是两种协议，分别记录；确定性复核优先使用固定计算预算。
- 降级率计入请求引擎，胜负对应实际执行策略链；同时报告请求引擎和备用策略，不能把备用策略胜利全部归功于主模型。
- 基础规则会提前结束，双方实际吃分可能未合计到 100；报告剩余未打出的分数，不能将停止时计分冒充完整打到底的净胜分。

输出至少包括双方赢副率、配对胜率差与置信区间、庄家成局率及合同分布、样本组数、P50/P95 决策耗时、超时/错误/降级率和重发牌统计。实验结论注明预算与样本条件。

### 7.3 布局与快捷键

牌桌与侧栏按实际可用宽度布局，支持调整侧栏宽度与收起；窄视口转为上下布局或抽屉。先验证常见笔记本与 1080P 场景中的完整手牌、16 张扣底手牌、当前墩与操作按钮可见，再增加花色矩阵。

| 快捷键 | 行为 |
|---|---|
| Space | 与 Next 按钮相同，最多推进一步 |
| Enter | 确认当前明确选择的操作 |
| Z / Cmd+Z / Ctrl+Z | 撤销并暂停 |
| Shift+Z / Cmd+Shift+Z / Ctrl+Shift+Z | 重做并暂停 |
| H | 请求当前座位 Hint |
| R | 按保存起点重开当前副或场景 |
| 1～4 | 为当前操作座位切换预设 Bridge / Algorithm / LLM / Laya；产生配置版本变化 |
| Esc | 关闭顶层弹窗或抽屉 |
| Tab | 保留原生焦点移动；选项卡在自身获得焦点后用方向键切换 |

首版已提供 Space / Enter、Z / Shift+Z、H、R、Esc 和原生 Tab；带 Cmd/Ctrl 的撤销组合及 1～4 引擎预设切换留待后续界面增强。

快捷键仅在工作台交互区域生效。输入框、textarea、contenteditable 和弹窗输入状态保留原生编辑行为；原生按钮的 Space/Enter 不额外触发第二次全局动作。长按和重复事件必须经过相同的提交保护。

## 8. 实施先后顺序

以下顺序按依赖与风险排列。每一步满足退出条件后，再开始依赖它的功能。布局修复可随对应 UI 接入完成，测试随能力交付，不集中到最后补齐。

| 顺序 | 交付内容 | 退出条件 |
|---|---|---|
| **1. 统一会话与执行调度** | 定义命令、游标和请求上下文；统一自动、单步、Next、Hint 的请求与提交；修复暂停、撤销、重开及旧结果失效；手动与自动动作均进入历史 | 延迟请求在撤销、重开和配置变化后不能修改局面；重复 Next 不重复提交；自动路径可撤销；matchEnd 行为正确 |
| **2. 全阶段合法接管与最小追溯** | 为当前行动座位提供叫分、定主、扣底、出牌控件；分离视图与控制状态；补齐阶段联合记录及评估/提交关联 | 四个座位、四个阶段均可合法接管；接管与 AI 请求竞争时状态一致；动作来源和降级可定位 |
| **3. 权威 JSON 快照与回放** | 建立版本化协议、规则恢复、阶段校验和完整导入导出；处理旧诊断片段；保存起点及命令序列用于回放 | 各阶段快照恢复后观察与合法动作一致、可继续结算；非法输入不替换原局面；保存动作逐步回放一致 |
| **4. 座位独立 profile 与信息投影** | 实现 Human/AI 路由、同类引擎不同参数、配置版本；同步本地/服务端生效配置；补齐全阶段观察边界 | 四 AI 可完成对局；同类模型不同 profile 不互相污染；普通请求不泄露暗牌；阶段不支持时明确降级 |
| **5. 同节点比较与参数重测** | 按请求隔离结果与思考流；使用全合法候选；按完成顺序展示；校验采纳上下文；加入 Prompt 草稿重测 | 同座位并行评估不串流；过期结果不能采纳；比较不自动推进；请求参数与实际配置可审查 |
| **6. 无界面配对评测** | 使用共享内核构建异步 Runner；增加阵营交换、座位轮换、独立随机源、并发限制及统计输出 | 同协议可复核；实验不污染 UI 会话；可取消；超时与降级归因正确；报告包含样本和不确定性 |
| **7. 历史分支保存与浏览** | 将线性历史升级为保留多个 child 的节点树；提供分支选择、比较和有界存储 | 撤销后新动作保留旧分支；切换分支不展示其他节点建议；多次评估与动作关联完整 |
| **8. 可视化场景编辑** | 先基于完整快照编辑；再设计独立无历史残局表示与能力检查；调整合同、牌张、比分与领出者 | 编辑使用阶段校验；构造来源和历史完整性可见；不支持无历史输入的引擎不会误运行 |
| **9. 验证并接入 Oracle** | 修复 DDS 当前墩、目标及精确性契约；建立独立全信息评估入口与 regret 展示 | 与独立小规模穷举一致；截断不冒充精确；完全信息与普通策略输入严格隔离 |
| **10. 紧凑格式与高级诊断** | 为已稳定的场景协议制定 YZF-FEN；补充 DDS 统计、概率与熵图、花色矩阵等 | 格式信息边界明确且往返测试通过；指标有来源和语义；UI 只展示引擎实际提供的数据 |

首个可用闭环是 **步骤 1～3**：暂停或接管一局、定位真实执行动作、导出坏局、导入后继续调试。算法比较闭环在 **步骤 4～6** 完成。后续增强不能反过来阻塞基础修复。

## 9. 验收与回归策略

### 9.1 执行与并发

- 用可控延迟的假引擎验证：计算中撤销、重开、导入、手动接管、修改模型或 Prompt 后，旧进度和结果不能更新活动会话。
- 覆盖返回过快、返回过晚、忽略 Abort、异常、超时和备用策略的路径。
- 单步预计算和 Hint 不产生动作节点；Next、自动动作及手动接管每次成功只产生一个节点。
- 自动运行撤销后保持暂停，不立即重走；重开不能撤销回到其他会话。
- 四个阶段均拒绝错座位与非法动作；四 AI、多个 Human 座位及 matchEnd 分别验证。

### 9.2 快照与规则

- 通过合法动作生成 bidding、trump、bury、playing 中途、提前 handEnd 与 matchEnd 样本，再做编解码往返。
- 校验恢复后的状态、规则函数、阶段观察、合法动作和继续执行结果；不只比较 JSON 字符串。
- 覆盖扣底阶段底牌引用、上一墩重复引用、四家不等长手牌、提前结束剩余牌和牌分守恒。
- 对未知版本、缺字段、重复牌、非法分档、错误计分、错误墩顺序等输入，验证可定位错误和原会话保持不变。
- 回放已保存动作得到相同节点摘要；模型重新推理与动作回放分别验收。

### 9.3 配置、信息与评测

- 覆盖四座路由、同类引擎不同参数、本地/服务端 profile 同步、阶段能力不足和实际降级归因。
- 隐藏牌分布改变但普通观察相同时，固定搜索随机源下的普通决策输入保持一致；测试所有决策阶段。
- 多引擎同座位并行时，进度、响应、指标和采纳动作按 requestId 隔离。
- 验证批跑配对分组、阵营交换、取消、并发上限、统计口径和实验导出。
- Oracle 单独使用小规模穷举与界限测试验收；精确性未达标前不展示精确 regret。

### 9.4 UI 与回归范围

当前静态渲染测试不足以覆盖 Hook 异步竞态与真实操作。补充运行内核行为测试，以及接管、快捷键、粘贴导入和窄屏布局的交互验证。

实施时先运行与变化相关的规则、引擎和工作台测试，并完成项目要求的类型检查与构建。每步通过其退出条件后再扩展范围；记录尚未支持的能力，避免用测试数量或统一“100%”口号代替具体行为验收。
