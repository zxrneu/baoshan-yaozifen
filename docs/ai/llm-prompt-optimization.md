# LLM Prompt 2.0 优化与验证记录

> 文档类型：历史对照记录；证据日期：2026-10-12。Prompt 2.0 / 套件 1.2.0；不证明整局牌力提高。返回[文档索引](../README.md)。

日期：2026-10-12；提示词版本：`2.0.0`；场景套件：`1.2.0`。实现见 [llmPrompts.ts](../../src/ai/engines/llm/llmPrompts.ts)，原始报告/请求/响应见[专项产物索引](../../experiments/results/engine-model-eval/prompt-v2-20261012/README.md)。

本次调整四阶段指引及上下文事实。在同配置的35场景单次对照中，原提示词通过 **22/35**，新版通过 **26/35**，阶段宏均分 **80 → 85**；两者最终动作均合法，新版零回退、原版有一次非法扣牌回退。改善8例、回退4例；仍有9例未通过，不能据此认定稳定优势或实战牌力提高。

## 1. 调整内容

| 部分 | 原问题 | 新行为 |
| --- | --- | --- |
| 通用规则与输出 | 大师角色、绝对化战术、各阶段重复要求思维链 | 分开规则、事实与策略；JSON动作在前，thinking仅一句决策依据，结论与动作一致 |
| 叫分 | 长套必清主、短门必有利、启发式估值容易变成叫分锚点 | 区分基础起叫、强控高叫与竞争再叫；不把自带分/HCP当最终吃分，未知底牌和明牌收益不能支撑盲目加价 |
| 专家建议消融 | 只隐藏suggestedBid，仍发送引导性战术建议 | `disableBidAdvice`移除整个bidAdvice，客观手牌与公开叫分信息保持相同；默认参考标为未校准、可忽略 |
| 定主 | 把分牌加权成控制力、机械只选最长 | 比较长度与连续顶张；用`topRunFromAce`替代混合strengthScore，明确只统计A至10 |
| 扣底 | 只扣短门，控制张虽合法却被当废牌；空门/五张门机会标记不准确 | 比较四张组合的保主、留控、造绝门；标记控制张代价，只有1～4张全非分副牌可在当前额度扣空 |
| 出牌 | 当前领先与稳赢混用，可能错误喂分或保留分牌 | 提供当前赢家、搭档稳赢标记、后手对手、每候选出后赢家；安全喂分优先兑现团队分 |
| 公开信息 | 公开手牌统一命名为搭档手牌；遗漏本人已知扣牌 | `revealed_hand`带座位及阵营，支持公开对手手牌；保留庄家已知扣牌和手牌数量/轮次 |
| 记牌与目标 | 缺少已升高赢张和合同目标 | 候选标记该门是否无更高未出牌；给出庄/闲距锁定胜负所需分数；该门最大不等于不会被将吃 |
| 输入冗余 | 本人手牌、座位名、逐牌分数反复出现 | 出牌只保留一份分门手牌与完整历史，候选使用cardId；删除误导的revealed_partner_hand字段 |

外部返回契约仍是bid/trump/cards/cardId等原字段，解析器、服务协议、模型选择、默认`low`思考档位与超时配置保持不变。提示词版本写入每阶段user正文；评测源码指纹变化会排除旧缓存。

## 2. 真实模型对照

两版均用部署别名`qwen38_27b`、chat、json_object、**none**、30000 ms超时、并发1、保留专家参考、关闭Mock。输入与裁判相同，35份`inputObservation`逐条相等；每版本每场景执行一次。

原提示词取自提交`c2819c8`，在独立进程中替换构造器，未改工作区代码。当前公共实现的`codeHash`与原提示词的`promptVariant/promptSourceHash`同时记录；新版代码指纹为：

```text
6d7bb7f8b4faeee549150a88e7efb189958caf8349e62f940f1a4655f49ff298
```

以上是两版评测当时共用的源码指纹。收尾时工作区另有扣底兜底修改，整体指纹已改变；逐条重建确认当前35份提示词仍与新版真实请求完全一致。原/新提示词源码快照、评测指纹和收尾工作区指纹分别保存在专项目录与comparison.json，未改写旧manifest。

[原版报告](../../experiments/results/engine-model-eval/prompt-v2-20261012/legacy-1791792714171-qwen38_27b/report.md)与[新版报告](../../experiments/results/engine-model-eval/prompt-v2-20261012/run-1791792478689-qwen38_27b/report.md)：

| 阶段 | 原版通过 | 新版通过 | 阶段均分 | 调用P95（原 → 新） |
| --- | --- | --- | --- | --- |
| 叫分 | 5/8 | 6/8 | 79 → 83 | 2391 → 2180 ms |
| 定主 | 6/7 | 7/7 | 86 → 90 | 2438 → 2212 ms |
| 扣底 | 6/8 | 6/8 | 81 → 84 | 3414 → 2787 ms |
| 出牌 | 5/12 | 7/12 | 72 → 81 | 4095 → 3351 ms |

整体P50为 **2254 → 1910 ms**，P95为 **3414 → 2787 ms**；这是本轮调用耗时，不是产品端到端延迟，也未采集服务排队或token usage。原版一次扣底返回不在手牌中的`3S`，被解析器拒绝后回退；回退动作计入最终分数，不代表模型原生成功。

普通起叫、再叫、副牌K保护、小主毙杀/超毙及搭档跨花色喂分等8例由未通过变为通过。以下4例反向变化，需继续诊断：

| 场景 | 原版动作（通过） | 新版动作（未过） |
| --- | --- | --- |
| `bid-strong-high-bid` | 叫 100 分 | 叫 80 分 |
| `bury-create-single-void` | 扣底 [3D, 2D, KC, 8C] | 扣底 [6S, 8C, 3D, 2D] |
| `play-second-hand-low` | 出牌 2D | 出牌 KD |
| `play-safe-exit` | 出牌 3S | 出牌 10D |

其余未过样例包括特长套仍叫80、扣底单K保护、领牌兑现副牌、第三手争大及领搭档绝门/兑现升高K。按scenarioId查[逐场景对照](../../experiments/results/engine-model-eval/prompt-v2-20261012/comparison.json)和NDJSON中的输入、候选、requestPayload、rawText、thinking与扣分原因。

过程记录也保留：叫分初稿6/8，第一次全阶段修订25/35，最终版26/35。第一次全阶段叫分7/8，最终同一叫分指引却是6/8，说明单次响应有波动，不能挑最好一轮代表最终配置。

## 3. 字符数与延迟边界

固定35场景的system+user平均字符数如下，来自[请求长度记录](../../experiments/results/engine-model-eval/prompt-v2-20261012/request-size-comparison.json)：

| 阶段 | 原版字符数 | 新版字符数 |
| --- | --- | --- |
| 叫分 | 2338 | 2246 |
| 定主 | 1916 | 1972 |
| 扣底 | 3078 | 3244 |
| 出牌 | 2615 | 3124 |

叫分减少了引导性建议，其他阶段补充预计算事实后输入可能增加。删除重复字段不等于总输入/token量一定减少；本次不能将耗时变化全部归因于提示词长度或输出顺序。没有要求模型公开内部推理，thinking只是供用户看的简短依据。

## 4. 验证与后续

- 提示词修改后**310项测试、25个测试文件通过**；包含同期新增扣底回归的最终工作区共**318项测试、26个文件通过**。TypeScript检查与生产构建通过；构建仍有原有bundle大小提示。
- 新增11项信息/契约回归：完整消融、连续顶张、扣空额度、控制张代价、领先与稳赢、候选超车、公开对手手牌、已升高K、已知扣牌及35场景输出解析。
- 本次模型比较只在none档运行，不能证明默认low档的准确率或长尾改善；未做同版多次重复、独立保留集或全局对战。
- 后续先按同服务条件重复none/low与专家建议开/关，再用独立牌局验证；优先排查上述4例回退以及解释正确但动作字段不一致的输出。

```bash
pnpm eval:llm --reasoning none --format json_object --timeout 30000 --concurrency 1
pnpm eval:llm --reasoning low --format json_object --timeout 60000 --concurrency 1
pnpm eval:llm --reasoning none --format json_object --timeout 30000 --concurrency 1 --disable-bid-advice
```

提示词结构参考[OpenAI官方reasoning best practices](https://developers.openai.com/api/docs/guides/reasoning-best-practices)：简洁直接、区分输入区域、不要求逐步公开推理。Qwen部署的实际效果以本项目评测为准，不从该文档推断模型表现。
