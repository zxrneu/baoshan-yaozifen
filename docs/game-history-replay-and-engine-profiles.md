# 对局数据库、复盘与引擎配置实例设计

> 更新日期：2026-10-12 · 状态：待实现的设计与验收规格。
>
> 已确定：**SQLite 保存对局；现有 Bridge / Algorithm / LLM / System One 支持多个独立配置实例；通过 HTTP 提供决策；玩家按名称选择配置并模拟对战。** 当前执行顺序和任务编号以 [开发路线](development-roadmap.md) 的 P0–P3 为准。

## 1. 首个闭环与实现起点

首个交付是：打一副牌 → 自动保存 → 重启后从历史列表打开 → 按真实动作逐步复盘。后续交付是：选择不同引擎配置 → 从同一历史节点继续模拟 → 保留原路径与新分支 → 批量换边对战 → 从报告打开某副牌复盘。

| 现有基础 | 当前限制 | 复用方式 |
| --- | --- | --- |
| `GameSession.commit` 统一执行动作并产生前后节点 | 历史只在内存，超过 1000 节点截断；撤销后落新动作裁掉原后续 | 持久化挂在提交边界；数据库路径不随内存窗口截断；后续升级保留多个 child |
| `getReplay`、快照导入导出和校验 | 保存有界线性路径；配置只含 `activeEngine` | 复用动作重放和规则校验，扩展版本化节点及配置引用 |
| `decisionLogger` 有评估与提交关联 | 决策最多 200 条；不能作为历史数据库 | 作为实时诊断缓存，完整评估另写数据库 |
| 现有四类引擎、RPC 与服务端注册表 | 默认每类型一份配置，全局活动引擎；RPC 配置覆盖主要针对 LLM | 增加 profile 注册与按座位路由，保留现有四类实现 |
| 配对对战脚本与 NDJSON | 未与产品历史、配置实例和复盘入口连接 | 复用规则和配对统计；通过同一 Repository 保存批跑轨迹 |

现有进程内 `game-1` 等序号不能直接作为跨重启数据库主键。持久身份使用稳定唯一 ID，运行时的 epoch/requestId 用于防止旧请求落入新节点，不代替历史 ID。

## 2. SQLite 落地边界

首版复用现有 **Node 服务 + HTTP API**：服务持有 SQLite 文件，浏览器通过 API 保存和查询，批跑也经同一 Repository 落库。`pnpm dev` 内置中间件与 `pnpm server` 复用服务实现；无需先建设账号、云同步或多人房间。

数据库位置通过 `.env` 的 `GAME_DB_PATH` 配置；采用迁移版本、事务和明确的文件备份方式。驱动在 P0.1 确认，验证项目 `node >=22` 的最低版本与 CI Node 24；不能假定所有 Node 22 小版本有相同 SQLite 能力。此设计不提前增加依赖。

`HistoryRepository` 隔离 SQL 与 UI/规则。`src/engine/` 不访问数据库。Tauri 无 Node 服务的纯离线运行后续增加原生 SQLite 适配；首版不声称该场景已经可以持久化，也不为此改用第二套历史协议。

普通对局、工作台接管、历史分支和批跑共用数据模型，来源分别标记。重开/放弃的副牌同样可保存，不只存正常结束的赢家和比分。

### 2.1 数据对象与关系

以下为逻辑对象，最终列定义、索引和迁移脚本在 P0.1 落实。结构化查询字段单列，完整快照、观察和配置使用版本化 JSON。

| 对象 | 必需内容 | 作用 |
| --- | --- | --- |
| `matches` | ID、起止时间、来源、状态、目标胜副、规则版本、应用/规则实现版本 | 一场可包含多副；区分进行中、完成、放弃和失败 |
| `hands` | matchId、副号、起始完整快照、结果、庄家、叫分、主牌、未打出分 | 保存实际起点与结算，重发牌过程也可追溯 |
| `branches` | handId、来源节点、分支名称、末节点、原路径/实验标记 | 原始路径与“如果这样打”分支并存；首版先有默认分支 |
| `action_nodes` | 稳定 ID、parentId、branchId、顺序、动作、来源、状态摘要、checkpoint 引用 | 真实执行路径；人工动作、AI、采纳建议及下一副分别表达 |
| `evaluations` | nodeId、requestId、座位、阶段、观察、候选、推荐、状态、耗时、回退及配置版本 | 多次评估可附同一节点；未采用建议不算执行动作 |
| `engine_profile_versions` | profileId、不可变版本/hash、类型、名称、脱敏参数与实现/Prompt 版本 | 历史使用当时配置，当前配置改变不改写旧局 |
| `seat_assignments` | handId/branchId、配置变更所在节点、四座 Human 或 profileVersion 引用 | 还原每一步由谁决策，同类型不同参数彼此独立 |
| `simulation_runs` / `simulation_boards` | 配置版本、种子集合、换边协议、进度、状态、组级结果、对局引用 | 批跑报告下钻到每副牌，取消或失败保留已完成记录 |

P0 先交付历史所需对象，模拟表随 P3 增加；P0 可先用“默认引擎配置快照”填入版本记录，不等待多配置 UI 才能存牌局。

### 2.2 保存一致性与恢复

- 只有规则校验成功并实际提交的命令进入动作路径。评估、Hint、取消和失效结果单列；切换配置另记版本/座位路由变化。
- 动作节点、分支游标与结算摘要在一个事务中保存；节点 ID/提交 ID 保证重试幂等。按会话顺序写入，不允许后写覆盖新节点。
- 保存进度在事务提交后确认。失败时显示“未保存”、保留待保存内容并暂停自动推进，允许重试；不能继续显示保存成功。
- 启动恢复到最后确认保存的节点。记录规则版本、起始快照和动作，不能只存 seed 或屏幕文字来声称可以重放。
- 每副起点、配置变更及适当间隔保存 checkpoint；回放核对节点摘要。未知规则/不兼容版本显式拒绝或迁移，不能套当前实现静默重算。
- 历史分页并按时间、状态、来源、引擎、叫分等查询；备份/导入导出沿用校验。数据库升级失败保留原文件，不以清空历史恢复启动。

## 3. 复盘与分支模拟

### 3.1 先交付原路径复盘

历史列表展示日期、来源、四座引擎、庄家/叫分/主牌、结果及未完成状态。打开一副牌后：

1. 从保存的起始快照与实际动作恢复，不重新请求模型。
2. 支持上一步、下一步、跳到某轮/阶段、播放和暂停；调用现有规则转换及快照校验。
3. 同步牌桌、当前动作、赢家、得分与该节点的决策记录；没有记录时显示未采集，不推测模型当时为何这样打。
4. 逐座位查看当时可见信息；全牌复盘与普通 AI 的输入投影分开。历史库里即使有完整牌局，也不能整包发给决策服务。
5. 原路径只读。复盘操作不触发自动 AI、音效反复播放或活动牌局提交；恢复未完成副牌是独立、明确的继续操作。

验收覆盖叫分、定主、扣底、中途跟牌、100 分公开手牌、提前结算和跨副；每个节点的合法动作、观察、计分与终局一致。模型断网也能查看已保存动作及诊断。

### 3.2 再交付“如果这样打”

从任意合法节点创建新分支；可手动换一个动作，也可更换后续座位配置再模拟。保留原节点、原后续、分支起点和新配置版本；不要直接修改原局或覆盖数据库原路径。

分支界面比较后续动作与实际结算。相同起点下的不同动作/策略结果用于诊断，单个分支的胜负不等于统计牌力提升。切换分支、配置或节点使旧请求失效。

## 4. 引擎创作范围：多配置实例

首版允许玩家配置当前支持的引擎。LLM、System One 可在文件中定义多条服务/模型配置；Bridge、Algorithm 可定义多组已有可用参数。配置后按名称选择、按四座分别分配，或把一组用于南北、另一组用于东西。

本轮交付配置模板、校验、列表与参数编辑；代码插件、上传任意脚本及新推理框架另立范围。System One 继续复用当前 `laya` 类型和 `/v1/systemone` 适配，不因显示名称新增第二种模型协议。

### 4.1 配置文件与不可变版本

拟新增版本化配置文件，例如 `engine-profiles.json`，由 `.env` 的 `ENGINE_PROFILES_PATH` 指定；同时提供无密钥的示例模板。文件是当前配置来源，SQLite 保存每次实际使用的脱敏版本。

| 公共字段 | 含义 |
| --- | --- |
| `id` / `name` / `type` | 稳定配置身份、玩家可读名称、现有四类引擎之一；多个 id 可以有相同 type |
| `options` | 按 type 校验的参数，不接受任意未实现字段 |
| `fallbackProfileId` | 显式备用配置，校验无环并记录实际采用者 |
| `capabilities` | 可提供模型决策的阶段与启发式阶段；不支持部分阶段时明确组合策略 |
| `version` / `configHash` | 从实际配置与实现/Prompt 标识形成版本；修改生成新版本，不更新历史引用 |

| 类型 | 首批可配置范围 |
| --- | --- |
| LLM | 多组端点/模型、chat/completion、响应格式、reasoningEffort、timeoutMs、重试、并发、bidAdvice 设置 |
| System One（laya） | 多组端点/模型、timeoutMs、降级配置；扣底目前为启发式，单列来源 |
| Bridge | fast/deep、minWorlds、maxWorlds、timeLimitMs、endgameCardLimit |
| Algorithm | 现有优化搜索预算与策略开关；只暴露实际支持且传入运行器的字段 |

公网端点、密钥及实际认证从 `.env` 解析，文件中使用环境变量引用，例如 `baseUrlEnv`、`apiKeyEnv`；完整凭据不进入浏览器配置列表、历史库或导出。历史只保留脱敏配置、端点标识及版本，不能靠重新读取当前文件“还原”旧参数。

旧单配置设置迁移为默认 profile；同类的多 profile 不共享可变模型/参数状态。正在执行的副牌固定其配置版本，配置重载用于之后创建的副牌或新分支；局内显式切换配置按所在节点另记版本，不回写已保存结果。

### 4.2 HTTP 决策与配置路由

扩展现有 `/api/decision`，以 `profileId` + 版本标识选择服务端注册配置；迁移期兼容旧 `engineType` 默认映射。引擎列表/健康查询提供多配置名称与状态，不能只返回每类型一项。

请求包含 requestId、阶段观察、合法候选、配置身份和总预算；响应记录请求配置、实际配置/引擎、动作、耗时、状态及回退链。完整历史状态和 seed 只供保存/裁判使用，不进入普通决策请求。

服务端按实例创建/复用独立配置，LLM/System One 多端点均真实生效，Bridge/Algorithm 参数也真正传入搜索。不能仅改变 UI 下拉框或响应标签。四座使用同类型不同参数时应能并行隔离、取消和追溯。

## 5. 模拟对战与历史互通

先复用现有共享规则和配对思路，补 profile 路由、独立会话、独立日志和数据库写入。批跑不使用活动牌桌的全局 logger/thinking 槽位。

支持两种入口：从保存的历史节点做后续模拟；从正常发牌集合做全生命周期换边对战。出牌消融固定前三阶段，完整策略对战允许合同变化，两种报告分开。

每次 run 固定配置版本、规则/代码版本、座位路由、发牌集合、搜索随机源和计算预算；设置并发上限、总量限制、重发牌/动作数上限及取消。退出后保存已完成副牌和进度，按组 ID 防止重复计数。

报告包含实际赢副率差及组级区间、合同/成约分布、耗时、故障、回退和未打出分；点击任一组可打开其两局复盘。执行失败不能混成非法牌，也不能静默删掉失败组提高成绩。小批跑验证流程；更强结论和默认替换仍通过 [统一评测](ai-engine-model-evaluation-plan.md)。

## 6. 验收原则

数据库与历史回放无需等模型牌力改进才开始。首版使用已有本地/服务端引擎完成闭环，多模型选择和大样本比较逐步增加。

每阶段先写与变更相关的行为测试：事务失败/幂等/恢复、逐节点回放、原分支保留、同类型配置隔离、四座 HTTP 路由及隐藏信息边界。涉及数据库使用临时 SQLite 文件，故障显式注入，不依赖默认端口或真实模型在线。

完成改动前通过 `pnpm test`、`pnpm build`；修改 Tauri 原生适配另跑项目要求的 Cargo 检查。SQLite 驱动、迁移和运行环境的具体选型随 P0.1 记录，不在设计中把未实现能力标为完成。
